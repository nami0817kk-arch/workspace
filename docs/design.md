# 設計メモ

## なぜ「AI に全部聞く」形にしなかったか

Claude に「おすすめの副業は？」と聞けば答えは返る。しかしそれだと、

- 毎回違う答えが返り、比較できない
- なぜその順位なのか説明できない
- 前回どこまで進んだかが残らない

という問題がある。そこで役割を分けた。

| 担当 | 内容 |
|---|---|
| Claude | アイデア出し、市場調査、文章生成、レビューの言語化 |
| こちら側のコード | 適合スコア、見積もり計算、進捗集計、データの保存 |

**判断の根拠になる数字は必ずコード側で決定的に計算する**。
これで「なぜ1位なのか」「なぜこの金額なのか」を毎回同じ基準で説明できる。

## 適合スコアの式（src/ideas.py）

配点は合計 100 点。各項目はプロフィールを基準に 0〜1 に正規化してから重みを掛ける。

| 項目 | 重み | 正規化 |
|---|---:|---|
| skill | 25 | `skill_match / 5` |
| time | 20 | 週稼働時間に対して、超過するほど減点 |
| capital | 15 | 予算に対して、超過するほど減点 |
| speed | 15 | 目標期限に対して、超過するほど減点 |
| ceiling | 15 | `月収目安 / 目標月収`（上限 1.0） |
| competition | 10 | `(6 - competition) / 5` |

「小さいほど良い項目」（稼働時間・初期費用・収益化までの月数）は、
基準内なら満点、基準の 2 倍で 0 点になるようになだらかに減点する。
基準を少し超えただけで足切りにすると、惜しい案が消えてしまうため。

## 見積もりの式（src/pricing.py）

安請け合いを防ぐため、**手取りから逆算**する。

```
工数     = (実作業時間 + 実作業時間 × 0.2 × 修正回数) × (1 + (難易度 - 3) × 0.15)
必要手取り = 工数 × 希望時給 × (特急なら 1.3) + 経費
提示額    = 必要手取り ÷ (1 - プラットフォーム手数料率)
```

3プランは提示額に 0.7 / 1.0 / 1.5 を掛けるが、**対応範囲（工数）も同じ倍率で増減させる**。
そうしないと安いプランだけ時給が落ちて、結局は消耗する。

「受注ライン」は標準プランの額。これを下回る依頼は、断るか対応範囲を削って調整する。

## データ保存

SQLite ではなく `data/*.json` にしたのは、

- 中身を直接開いて直せる
- バックアップがファイルのコピーで済む
- 個人利用の規模ではパフォーマンス上の問題が出ない

ため。壊れた JSON を読んだ場合は退避して初期値に戻し、ツール自体は落とさない（`src/store.py`）。

## 自動化エンジンの設計（src/auto/）

### なぜ検品を二段にしたか

自動化の失敗は「生成できないこと」ではなく「駄目なものが誰にも見られずに納品されること」で起きる。
そこで性質の違う2つを直列に置いた。

| 段 | 検出できるもの | 検出できないもの |
|---|---|---|
| 機械チェック（`qa.mechanical`） | 文字数・必須項目の欠落・景表法NG語・AIの前置きやプレースホルダ残り | 内容が依頼に合っているか |
| AI検品（`qa.review`） | 依頼を満たしているか、指摘の具体性 | 自分が見落とした形式不備 |

重要なのは**機械チェックが AI の判定を上書きする**こと（`qa.check`）。
AI が「合格」と言っても、必須項目が抜けていれば不合格にする。
LLM に最終判断を委ねると、この種の見落としは必ず起きる。

### 修正ループを1回に制限した理由

修正を回すほど品質は上がるが、原価は線形に増える。
実測では 1 回の修正で原価が約 2 倍になる（生成 + 検品 + 修正 + 再検品）。

2回目以降で直る指摘は、たいてい「入力情報が足りない」ことが原因で、
何度回しても直らない。そこで 1 回で打ち切り、`要確認` として人に上げる。
**人が見るのはここだけ**、という設計にするための線引き。

### 売上を「検品を通ったものだけ」計上する理由

`auto` が処理した時点では、まだ納品していない。
要確認の案件を売上に含めると、粗利率も達成率も実態より良く見えてしまう。

そのため `status == "done"` のものだけを計上し、要確認は人が直して
`job delivered` を実行したときに計上する（`jobs.record_sale`。二重計上はしない）。

### 原価計算

`llm.meter()` が API レスポンスの `usage` を集計し、
モデル別の公開単価（`llm.PRICING`）から円換算する。推定ではなく実測値。

キャッシュ読み出しは入力単価の 1/10、書き込みは 1.25 倍として計算する。
同じサービスを連続処理するとき system プロンプトがキャッシュされるので、
2件目以降は原価が下がる。

## メディア運営の設計（src/media/）

### 受託と何が違うか

| | 受託 | ストック型（アフィリ・広告） |
|---|---|---|
| 収益の決まり方 | 単価 × 件数（自分で決められる） | PV × 転換率 × 単価（自分では決められない） |
| 初報酬まで | 数日 | 数ヶ月（検索評価のラグ） |
| 労力と収益 | 比例する | 比例しない。積み上がるか、ゼロのまま終わるか |
| 失敗の形 | 案件が取れない | 書いたが順位が付かない |

同じ「AIで文章を作る」でも、判断すべきことが違う。
受託は「いくらで受けるか」、ストック型は「そもそもどこで戦うか」。

### 順位を計算に組み込んだ理由

アフィリエイトの試算でよくある誤りは、検索ボリュームをそのまま PV として扱うこと。
実際は順位別 CTR を掛けた分しか来ない。8位なら約 3%、つまり検索数の 1/33 しか読まれない。

そこで「難易度 → 現実的に取れる順位 → CTR → PV → 収益」という連鎖を全ての計算に通した。
これにより、難易度5（大手が独占）のキーワードは 15 位想定になり、
単価がいくら高くても期待収益が低く出る。実態に合った優先順位になる。

### 検索ボリュームを AI に推測させない

AI は検索ボリュームの正確な値を持たない。それらしい数値を出させると、
その数値の上に逆算とシミュレーションが積み上がり、全体が机上の空論になる。

そのため AI には「多い/中/少ない」の3段階しか答えさせず（スキーマで強制）、
実データは CSV 取り込みで入れる。推測値は表示上も `?` で区別する。
同じ理由で、ジャンルの案件単価も「低/中/高/特に高い」の段階評価に留めている。

### リライト優先度を「増える見込み額」にした理由

順位順やPV順に並べても、直す価値の順にはならない。
100PVを10位から3位にするより、1000PVを10位から3位にするほうが増分は大きい。

そこで実測PVと順位別CTRから実質的な検索ボリュームを逆算し、
3位まで上げた場合の増分収益を出して並べる。実測に基づくので、
「このキーワードは元々需要が無かった」ケースも自然に下位に落ちる。

### 実測でモデルを補正させる

既定パラメータ（CVR 2%、遷移率 5% 等）は一般値であって、その人の数字ではない。
`media check` で実測との比を出し、乖離が大きければパラメータ更新を促す。

ここを放置すると、逆算もシミュレーションも「それらしい数字」を出し続けるだけになる。
モデルは実測に合わせて初めて意思決定に使える。

## アプリ収益の設計（src/apps/）

### 継続率を冪関数で近似した理由

アプリのDAUは「毎日入ってくる人 × その人たちがどれだけ残るか」で決まる。
継続率は初日に急落し、その後はなだらかに減る。直線でも指数関数でもなく、
冪関数 `r(d) = D1 × d^(-k)` が実態に近い。

k は D1 と D30 の実測2点から一意に決まる（`k = log(D1/D30) / log(30)`）ので、
**ストアの分析画面で取れる2つの数字を入れるだけ**で曲線が確定する。
そこから積分すれば「1インストールが何日分のDAUを生むか」が出る。

D30 が D1 以上という不整合な入力でも落ちないよう、その場合は D1 を横ばいに置く。

### LTV と CPI を必ず並べて出す理由

個人開発で最も金を失うのは、継続率が低いまま広告を出稿することだと考えている。
LTV（1インストールが生涯に生む収益）が CPI（1インストールの獲得単価）を
下回っていれば、広告は打つほど赤字が増える。

そのため `app plan` は必ずこの2つを並べ、逆転している場合は警告を出す。
「インストールを増やす」より先に「継続率を上げる」を促す設計にした。

感度分析でも、D1 20%→60% で必要インストール数が 83件/日 → 8件/日 に変わることを示す。
穴の空いたバケツに水を注いでも意味がない、というのを数字で見せるため。

## ポートフォリオの設計（src/portfolio/）

### なぜ横断レイヤーが要るか

収益モデルが違うものを複数持つと、「どれに時間を割くか」が最大の意思決定になる。
だが個々のモデル（アプリ・メディア・受託）は自分のことしか知らない。

そこで共通の記録形式（月・収益・原価・時間）だけを持つ層を上に置き、
実績時給と成長率で横に比較できるようにした。
収益モデルごとの見通しが必要なときは `pjt forecast` が種別で振り分ける。

### 判定ロジックを記事のリライト判定と揃えた

`media/analytics.py` の記事診断と同じ構造にしてある。

  実績から状態を分類する → 状態ごとに打ち手が決まっている

記事もプロジェクトも、判断すべきことは同じ「続けるか、直すか、やめるか」だから。
同じ考え方で揃えておけば、片方に慣れればもう片方も読める。

### 時間配分を「最適化」と呼ばない理由

判定ごとの重み（伸ばす3.0 / てこ入れ2.0 / 様子見1.0 / 撤退0.0）で按分しているだけで、
これは最適化ではなく方針の表明にすぎない。

限界収益を正しく推定するには、時間を追加投下したときの収益増加が分かっていないといけないが、
そんなデータは個人の副業規模では取れない。取れないものを推定したふりをして
それらしい数字を出すのが一番危険なので、**根拠の数字を併記したうえで
「最終的には運営者が決めるもの」と明示する**設計にした。

### 成長率の比較窓を可変にした

固定で「直近3ヶ月 vs その前の3ヶ月」にすると、記録が5ヶ月たまるまで
成長を判定できない。立ち上げ期こそ伸びているかどうかを見たいのに、
その時期だけ判定できないのでは意味がない。

そこで窓を `min(3, 記録数 // 2)` とし、2ヶ月分あれば比較できるようにした。
表示にも「直近◯ヶ月」と実際に使った窓を出して、精度の限界が分かるようにしている。

## ダッシュボード画面の設計（src/screen.py）

### なぜ Web アプリにしなかったか

収益の実績は個人情報そのもので、サーバに置く理由が無い。
サーバを立てれば起動の手間と管理コストがかかり、続かない。

そこで **単一の静的 HTML を生成するだけ** にした。
外部ライブラリも通信も使わないので、ファイルをダブルクリックすれば
オフラインで開き、データが手元から出ることもない。

CDN からグラフライブラリを読むと、オフラインで開けなくなるうえに
閲覧の事実が外部に漏れる。そのため SVG は Python 側で組み立てている。

### 色の決め方

系列の色は検証済みのパレットをそのまま使い、
色覚特性のシミュレーション上での識別距離を検証スクリプトで確認した
（light / dark とも全項目 PASS）。

ただし light モードでは一部の色がコントラスト 3:1 を下回るため、
その場合の救済として次を必ず入れている。

- 2系列以上では凡例を必ず出す（色の一致だけで読ませない）
- 判定バッジは色と文字ラベルをセットにする
- 同じ数値をテーブルにも出す

### 軸の上限の決め方

目標月収に合わせて軸を取ると、実績が目標よりはるかに小さい立ち上げ期に
棒が潰れて何も読めなくなる。かといって実績だけに合わせると、
目標との距離が見えなくなる。

そこで **目標線の表示上限を実績の3倍まで** とし、それを超える場合は
実績側にスケールを寄せる。目標との距離はヒーロー数値のメーターが担う。

### 収益ゼロの時期を隠さない

最初の設計では「今月の収益」と「目標達成率」を主役にしていた。
だが収益が立つ前の時期にこれを見せると、大きな 0 と 0% が並ぶだけで、
判断材料にならないうえ、続ける気力も削ぐ。

実際には、その時期に知りたいのは次の3つ。

- いくら使ったか（回収すべき額）
- 毎月いくら出ていくか（放置したときの増え方）
- 最初の1円まで何が要るか

そこで収益が 0 のあいだは **投資フェーズ表示** に切り替える。
主役の数字は「まだ回収していない額」、メーターは目標月収ではなく
「まず支出と同額」を最初の線として置く。到達すれば、
少なくとも続けるほど損が増える状態ではなくなるため。

グラフも「収益の推移」から「収支と累積損益」に変えた。
収益ゼロなら棒は下にしか出ないが、それが実態なので隠さない。
累積線が下がり続けているのか底を打ったのかが、一目で分かることを優先した。

### 定額制と従量課金で原価の意味が変わる

当初、原価は API のトークン単価からしか計算していなかった。
だが AI を定額（サブスク）で使っている場合、**1件作るごとの追加費用は発生しない**。
月額は固定で、10件作っても100件作っても支出は変わらない。

この違いは表面的な計算式の差ではなく、判断が変わる。

| | 定額 | 従量 |
|---|---|---|
| 1件あたりの追加費用 | 0円 | トークン数に比例 |
| 量を絞る理由 | 費用面には無い | 増やすほど原価が増える |
| 損益分岐 | 月額を回収できる件数 | 件数によらず粗利率で決まる |

そのため `profile` に課金形態を持たせ、次を分岐させた。

- `cost --estimate` は「月額を回収するのに何件必要か」の表に変わる
- `media simulate` の記事1本あたり原価が 0 になる
- `pjt sync` は案件ごとの原価を実費として計上しない
  （月額は経費に1本で入っているので、載せると二重計上になる）

案件ごとに記録しているトークン原価は、定額制では「従量だったらいくらか」の
参考値として残す。将来 API に切り替える判断材料になるため。

### 経費を独立させた理由

当初、支出はプロジェクト単位の原価しか記録できなかった。
だがツールの利用料のように、どのプロジェクトにも按分しにくく、
しかも収益ゼロの時期に唯一発生している支出がある。

これを記録できないと、画面上は「支出ゼロ・収益ゼロ」に見えてしまい、
実態と食い違う。そこで共通経費を独立させ、
継続課金は開始月の指定だけで各月に展開されるようにした（毎月手で入れると続かないため）。

### 入力のエスケープ

プロジェクト名やタスク名は自由入力で、それが HTML に埋め込まれる。
自分しか使わない画面でも、`<` を含む名前を付けただけで表示が壊れるのは困る。
全ての差し込み位置で `html.escape` を通し、テストで検証している。
