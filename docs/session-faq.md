# セッション FAQ — ユーザーに聞く前にここを読む

workspace で作業する Claude セッション向け。ここに無い疑問は
`docs/coordinator.txt` に書かれた調整役セッションへ **SendMessage** で聞く。
**ユーザーへの質問は最終手段**（調整役が不在・応答しない・ユーザーにしか決められない事項のみ）。

## 構成・場所

- **全PJTはモノレポ `C:\Users\なみ\dev\workspace`**（private、nami0817kk-arch/workspace）。
  旧 dev/ 直下の個別フォルダ・個別リポジトリは**もう使わない**（アーカイブ待ち）。

- 新しいPJTを足したら: `projects/<name>/` に置き、`<name>-tests.yml` を既存パターン
  （python-tests.yml の workflow_call）で作り、ルート `.github/dependabot.yml` の
  pip `directories:` に追加する。

## 作業の始め方（規約の要点）

- **メインツリーで checkout 禁止。必ず worktree**:
  `git -C C:/Users/なみ/dev/workspace worktree add C:/Users/なみ/dev/wt-<topic> -b claude/<topic> origin/master`
- 区切りごとに push（WIP可）。毎晩22時の wip-sweeper が未pushを `wip/` へ退避するが保険にすぎない。
- 小さな単一PJT変更は master 直 push 可（worktree 上で）。それ以外は fetch→検証→merge。
- **テストはローカルではなく CI で回す**（下の「テストはクラウドで回す」）。analyze は手元でよいが、通過条件は CI のテストに置く。

## よくある質問（実際に出たもの）

**Q. 旧リポジトリ（dev/ai-lab 等）で作業してしまった / 作業中のものがある**
A. ブランチを旧リポジトリの origin に push した上で、workspace 側から
`git subtree pull --prefix=<配置先> C:/Users/なみ/dev/<旧リポ> <ブランチ>` で合流させる。
衝突は「統合後に workspace 側が触った箇所」（projects.toml、入れ子 .github の削除等）に限られ、
**workspace 側を正**として解消する。

**Q. 入れ子の `.github/`（projects/*/github 等）が消えている**
A. 意図的。モノレポでは動かないため削除した。ワークフローの実体はルート
`.github/workflows/` にあり、変更したい場合はそちらの `<pjt>-*.yml` を直す。

**Q. soccer の web.yml が無い**
A. GitHub Pages が private リポジトリで使えないため意図的に未移植。
Cloudflare Pages 方式の `soccer-pages.yml` として作り直す（tool-factory-pages.yml が先例。
Flutter ビルドは `--base-href "/"` に変更が必要）。担当セッションが作業中。

**Q. kabu-daily / tool-factory-pages がデプロイ段で failure**
A. 既知。Cloudflare の Secrets（CLOUDFLARE_API_TOKEN / CLOUDFLARE_ACCOUNT_ID）の
ユーザー登録待ち。デプロイ以外のステップが緑なら正常。
`gh secret list` が空かどうかで、まだ未登録かを判定できる。

**Q. Cloudflare の API トークンは1本を使い回せるか**
A. **使い回せない。** 画像生成（imagegen の Workers AI コネクタ）用に発行したトークンでは
Pages デプロイができない。実測値:

| 叩いた先 | Workers AI 権限のトークン |
|---|---|
| `GET /client/v4/user/tokens/verify` | HTTP 200 `success: true` |
| `GET /client/v4/accounts/<id>/pages/projects` | **HTTP 403 Authentication error** |

`verify` が通るのでトークン自体は有効に見えるが、Pages API は権限不足で弾かれる。
**「トークンは有効」を Pages が使える根拠にしないこと。** 切り分けるなら
`pages/projects` を直接叩く。

用途ごとに別トークンを発行する。

| 用途 | 必要な権限（ダッシュボード → カスタムトークンを作成する） |
|---|---|
| 画像生成（imagegen） | アカウント / **Workers AI** / 読み取り |
| Pages デプロイ（CI の Secrets） | アカウント / **Cloudflare Pages** / 編集 |

`CLOUDFLARE_ACCOUNT_ID` は秘密情報ではない公開識別子なので両方で共用してよい。
**トークンの値を Claude セッションが `gh secret set` に投入するのは禁止**（認証情報の
取り扱いとして、調整役を含むどのセッションでも行わない）。登録はユーザーが実施する。

**Q. kabu の取得を CI に戻したい / 取得が動いていない**
A. kabutan は GitHub Actions の IP を 405 でブロックする。**CI からの取得に戻さない**。
取得はこのPCのタスク `kabu-daily-fetch`（平日16:10、projects/kabu-agari-ranking/run-daily.ps1）。
ログは同ディレクトリの run-daily.log。

**Q. youtube のテストが CI に無い**
A. **2026-09-01 に復活済み**（`youtube-tests.yml`、590件が ubuntu で緑・約1分）。
「マシン依存」の実体は**日本語フォント1つだけ**だった。VOICEVOX も ffmpeg も
テストは差し替えで動くので要らない。CI では `fonts-noto-cjk` を apt で入れている。
フォントのファイル名と置き場所は版ごとに変わるので、`config.FONT_CANDIDATES` で
当たらなければ `/usr/share/fonts` を舐めて探す（`config._font_in_system`）。

**Q. kabutan の解析を直したい**
A. 実体は `libs/kabutan`（kabu と qgt が共用）。公開名と出力列は両PJTのテストが
前提にしているので、変えるときは両方のテストを回す。

**Q. 他セッションの worktree・ブランチ・未コミットに遭遇した**
A. 触らない。報告も不要（作業中が正常）。自分の worktree で作業を続ける。

**Q. `git worktree remove` が「Permission denied」で失敗する**
A. Windows でディレクトリにハンドルが残っていると起きる。多くの場合**登録解除だけは完了していて、
空ディレクトリが残る**状態になる。`git worktree list` に出なくなっていれば、残ったディレクトリを
`rmdir <path>` で消せば整合が取れる（消えない場合はそのパスを cwd にしているシェルやエディタを
閉じてから再実行）。`git worktree prune` は登録が既に消えているため効かない。
ブランチ削除は別途 `git branch -D claude/<topic>` が要る。

**Q. projects/ai-blog が無い**
A. 2026-09-01 にユーザー判断でクローズした（テスト・CI・依存固定なしの最薄PJTで、投資判断の結果）。
書きかけ（generator.py 等）は git 履歴に残っている。復活させる場合:
`git log --oneline -- projects/ai-blog` で最終コミットを見つけ、`git checkout <sha> -- projects/ai-blog`。
**Q. master に追従したい / ブランチが遅れている（統合済みPJTを触っている場合）**
A. **`git rebase` を使わない。`git merge origin/master` で追従する。**
`projects/<pjt>` の多くは旧リポジトリを subtree merge（`merge -s ours` + `read-tree --prefix`）
で取り込んだもので、履歴には**元リポジトリのルート直下パスのままのコミット**が含まれている。
rebase はそれを現在のブランチ上に再生しようとするため、`projects/<pjt>/` 配下ではなく
リポジトリ直下にファイルを作ろうとして衝突する（2026-09-01、gemini-api 取り込み時に発生）。
衝突を手で潰しても履歴が平坦化されて取り込み構造が壊れるので、`git rebase --abort` して
merge に切り替えるのが正しい。新規追加した PJT でも、取り込みコミットを含むブランチは同じ。

**Q. growth を手元で回したい / 件数が他セッションの報告と合わない**
A. `growth run` の `--workspace` には **`growth fetch` で取得した実クローンを渡す**。
作業ツリーを渡すと、gitignore 済みのローカルファイルや他セッションの未コミット物まで
観測して誤検知が出る（実例: `projects/gemini-api/.env` は gitignore 済みで git 追跡も
履歴も無いのに、作業ツリー観測では `[critical] .env がリポジトリに入ってしまっている`
と判定された）。週次 Actions と同条件のクリーンクローンが正。

```
py -m growth fetch --workspace <scratch>/growth-ws
py -m growth run   --workspace <scratch>/growth-ws
```

`dismiss` は**誤検知・恒久的に対象外のものにだけ**使う。既に直って自動解決した項目に
かけると、恒久抑止だけが残って将来の退行を検出できなくなる。

**Q. soccer のセーブが大きい / 保存が重い**

**ストア申請前には着手しない**（セーブ形式が変わるため）。

## Dart / Flutter のリファクタで踏んだ罠（2026-09-01 実測）

game_state.dart(4733行)を part + extension で6分割したときに実際に出たもの。
同種の作業では最初に読むこと。

**flutter analyze の緑を安全網に数えない。テストのコンパイルを正とする。**
static を未修飾のまま解析したとき `No issues found` を返したが、
`flutter test` のコンパイルは10件以上のエラーで落ちた。実行時間が通常19秒に対し
9.5秒だったので解析サーバーのキャッシュと思われる。この分割作業で見つかった
不備5件は、すべて analyze ではなくテストのコンパイルが検出した。
通過条件は `flutter test` に置く。

**1つのクラスは複数ファイルに分割できない。**`part` はライブラリを分ける仕組みで、
クラス本体は分けられない。`extension Xxx on GameState` を part ファイルに置いて
メソッドを移す形になる。private(`_`)は Dart ではライブラリ単位なので、
part 間では素通しで触れる。

**移動すると参照の解決規則が変わる。4種類ある。**

- `notifyListeners()` は `@protected` かつ `@visibleForTesting`。extension から
  直接呼ぶと analyze が赤になる。クラス本体に `void _notify() => notifyListeners();`
  を1つ置いて経由させる。
- クラス直下の `static` への**無修飾参照**は解決されない。`GameState.xxx` と書く。
- 文字列補間の `$staticName` も同じ。`${GameState.staticName}` に直す。
- extension は**インスタンスフィールドを宣言できない**。フィールドと static 宣言は
  本体に残すしかない。

**自動置換スクリプトで区画を行番号で指定しない。**移動のたびに行番号がずれる。
しかも**ずれてもテストは通ってしまう**ため、意図と違うグルーピングに気付けない。
実際 `buyPlayer` が取り残されたまま無関係の領域が混入したが、453件は全部緑だった。
メンバー名から宣言行を毎回引き直すこと。

**Python の `\w` は Unicode 対応。**`$continentalTieWinPrize万円` の「万」が
単語文字と判定され、`(?![\w])` の否定先読みが成立せず置換が効かなかった。
日英混在のコードベースで識別子を置換するときは `[A-Za-z0-9_]` を明示する。

**ブロックの先頭は宣言行とは限らない。**`///` だけでなく `//` のセクション見出しも
飛ばさないと、直後のフィールドや static を「移せる」と誤判定する。

**Q. リモートデバッグの Chrome（ポート9222）はいつ閉じる?**
A. **使い終わったら閉じる。ログイン済みのまま放置しない。**
9222 を開けた Chrome は、そのポートに繋げる相手にブラウザ（Cookie・ログイン状態込み）を
丸ごと明け渡す。`127.0.0.1` に閉じてはいるが、開けておく理由がないなら閉じるのが原則。
生存確認は `curl -s -m 5 http://127.0.0.1:9222/json/version`（JSON が返れば起動中）。
閉じるのは普通にウィンドウを閉じるだけでよい（利用者の目の前にあるので、勝手に落とさず
一声かける。プロセスから落とすときは次項の PID 手順で普段使いの Chrome を巻き込まない）。
ログイン状態はプロファイルに残るので、次回起動
（`platform/ai-lab/scripts/start-chrome-debug.ps1`）でもそのまま使える。

**Q. Chrome 操作（ai-lab の control / romano-latest）が接続でタイムアウトする**
A. `connect_over_cdp: Timeout ... exceeded` が出るのに、
`curl http://127.0.0.1:9222/json/version` は応答し `/json/list` でタブも取れる、
という状態になることがある（2026-09-02 に発生）。ブラウザ内部の状態が原因で、
新規に立てた Chrome では起きない。**デバッグ用の Chrome を再起動すれば直る。
プロファイルは残るのでログイン状態も維持される。**

普段使いの Chrome を巻き込まないよう、**PID で特定して落とす**こと
（`Get-Process chrome` は通常の Chrome も含む。実測で34プロセスあった）。

```powershell
# 1. デバッグ用の親プロセスだけを探す
Get-CimInstance Win32_Process -Filter "Name='chrome.exe'" |
  Where-Object { $_.CommandLine -like '*remote-debugging-port=9222*' } |
  Select-Object ProcessId, CommandLine
# 2. --remote-debugging-port を持つ親（--type= が付いていないもの）を止める
Stop-Process -Id <親のPID>
# 3. 立て直す
powershell -ExecutionPolicy Bypass -File platform/ai-lab/scripts/start-chrome-debug.ps1
```

**Q. X（Twitter）の取得が1アカウント5件で頭打ちになる**
A. 未ログイン。ログイン済みプロファイルなら20件以上読める（実測）。
ログイン操作は利用者にしてもらう（スキルの決まり）。`x.com/login` を開くところまで:

```bash
curl -s -X PUT "http://127.0.0.1:9222/json/new?https://x.com/login"
```

ログインは**永続プロファイル側（9222、`%LOCALAPPDATA%` 直下の `ai-lab/chrome-debug-profile`）**で
行うこと。一時プロファイルで立てた Chrome に入れても、消えると失われる。

## Flutter の画面テストで踏んだ罠（2026-09-02 実測）

soccer の全画面を描画してレイアウト崩れを探したときに出たもの。**どちらも
「テストが通っているのに実は検査できていない」形の失敗**なので、同種の作業を
するなら先に読むこと。

**オーバーフローは try/catch では捕まらない。`tester.takeException()` を使う。**
RenderFlex のはみ出しは呼び出し側へ throw されるのではなく
`FlutterError.onError` に報告される。await を try で囲んでも何も捕まらず、
「全画面を描画したが例外は出なかった」という誤った結論になる。
pump のあとに `tester.takeException()` を呼んで回収する。

**テストで言語を指定するなら `SettingsController.init()` の後に書く。**
init() は保存値から `Tr.language` を上書きする。セットアップの前に
`Tr.language = AppLanguage.japanese` と書いても消され、端末ロケール(テストでは
英語)にフォールバックする。

この失敗は実際に起きた。日本語と英語で全画面を描画したつもりが、**両方とも
英語を描画していた。**発覚のきっかけは「日英で失敗した画面と、はみ出しの
ピクセル数が完全に一致している」という不自然さ。言語で幅が変わるはずのものが
1pxも違わないのはおかしい、と思って言語切替の確認を足したら、日本語側が
そもそも切り替わっていなかった。

実害もあった。修正対象の1画面(トレーニングの28pxはみ出し)は**英語でしか
起きない**。気づかず「日英で検証済み」として通していたら、日本語側の検査は
存在しないまま網が張られたことになる。

**教訓として、切り替えたつもりの条件は、切り替わったことをテスト自身に
確かめさせる。**soccer では各条件の冒頭で、その言語の見出しが実際に描画されて
いるかを見ている。今後同じ形で無効化されればテストが落ちる。

**プラグインを使う画面は、例外が遅れて届いて別のテストを落とす。**
実機のプラグインが無い環境では `MissingPluginException` / `PlatformException`
が出るが、これが**描画のあと、そのテストが終わってから**届くことがある。
flutter_test は「テスト完了後に投げられた例外」を直前のテストの失敗として
扱うので、**まったく無関係のテストが赤くなる**。原因のテストを見ても何も
起きていないので、非常に追いにくい。

soccer では設定画面(バージョン表示の `package_info`)と課金の初期化で踏んだ。
対処は、チャネルを差し替えて実機に行かせないこと。

```dart
TestDefaultBinaryMessengerBinding.instance.defaultBinaryMessenger
    .setMockMethodCallHandler(
  const MethodChannel('dev.fluttercommunity.plus/package_info'),
  (call) async => <String, dynamic>{'version': '1.0.0', ...},
);
```

注入できる設計になっているもの(課金・広告)は、モックのチャネルより
差し替え用の実装を渡す方が素直。`MonetizationController(adService:, purchases:)`
のように受け口があるかを先に見る。

**ついでに:** `testWidgets` は疑似時間で動くので、SharedPreferences を待つ
セットアップは `tester.runAsync()` の中で行う。外に書くと完了せず、テストが
制限時間まで固まる。また `pumpAndSettle()` は全アニメーションの停止を待つため、
終わらないアニメーションを持つ画面があると同様に固まる。はみ出しはレイアウト
時に出るので、`pump()` を数回打つだけで足りる。

## 外れた仮説の残骸を撤去する（2026-09-02 実例）

**真因が別だったと分かったら、効果のなかった変更は戻す。**残すと、直っていない
のに副作用だけが残る。

実例。選手検索の画面が縦に4pxはみ出していたので、`IconButton` が大きすぎると
考えて `VisualDensity.compact` を入れた。**これは外れで、テストは落ちたまま
だった。**真因は別で、最上位の `Column` の固定部分が画面高を超えていた。そちらを
直してはみ出しは解消したが、**外した方の変更を戻さずに残していた。**

結果、その `IconButton` はタップ領域が 48x48 から 40x40 に縮んだままになり、
翌日のアクセシビリティ検査で Android のタップ領域基準の違反として出てきた。
はみ出しを直した代わりに、押しにくいボタンを作っていたことになる。

**How to apply:** 「入れてみたが直らなかった」変更は、次の手を打つ前にその場で
戻す。まとめて後で消そうとすると、直った達成感で忘れる。commit を分けておくと
戻しやすい。

自分の変更を疑う目は、他人のコードを疑う目より働きにくい。**直したあと、
直した対象そのものを測り直す**のが唯一の防ぎ方だった。同じ日に、テストが
日英を検証できていなかった件も同じ形で見つかっている(上の節)。

## 条件付きで出る UI はテストされていない（2026-09-03 実例）

**画面を描画するテストは、その画面が「何も無い状態」しか見ていない。**
条件を満たしたときだけ現れる部分は、網の中にあるように見えて外にある。

soccer の `screen_render_test` は新規セーブで全画面を描画する。つまり、
警告カード・助言カード・実績解除の通知・各種の「〜が不足しています」の類は、
条件が立っていないので**一度も描画されない**。画面名は対象一覧に載っているので、
覆えているように見えるのが厄介なところ。

実害が出た。育成の助言カードは、該当する選手がいるときだけ出る。その見出し
(アイコン + "Development adviser")が英語・320px で右に28px溢れていたが、
カードが描画されたことが無かったため誰も気づいていなかった。同じカードに手を
入れたときも、ローカルでは**引き次第で描画されたりされなかったり**して、
CI で初めて落ちた。

**How to apply:** 条件付きの UI を足す・触るときは、その条件を満たす状態を
テストで作ってから描画する。「画面は網羅済み」を根拠にしない。

### 検証したい条件だけを作る

条件を作るとき、**他の条件は全員から取り除いてから**にする。生成物に依存すると
テストが引き次第で落ちる。

soccer の育成アドバイザーは上位6件で打ち切り、しかも表示順は種類の優先度で
決まる。優先度が最下位の提案(メンター未設定)を検証したいのに、ランダム生成
された選手団に疲労の助言が6件あると、検証対象がリストから切り捨てられる。
これで実際にテストが落ちた。

上位N件で打ち切る仕組み・優先度で並べ替える仕組みがあるときは、この相互作用を
疑う。テストの冒頭で全員を「助言が出ない状態」に均してから、見たい条件だけを
1つ作れば安定する。

## 自動チェックが緑でも、成果物そのものを見るまで完了と言わない（2026-09-03 実例）

テストが通り、点検コマンドが全項目 ✓ を返し、終了コードも全部 0 だった。
それでも**出来上がったものは壊れていた**、という事例。

youtube PJT で動画を2本作り、`review`（公開前の点検）が全項目 ✓、
`pytest` 663件緑、ffmpeg も exit 0 だった。そのまま「完成しました」と報告した。
あとでコンタクトシートを作って画面を見たら、こうなっていた。

- 見出しが熟語の途中で割れていた（「移／籍期限」「チ／ェルシー」「成／立」）
- まとめ画面が過密で、カードと下のテロップが重なっていた
- 反応カードのラベルが本文の最終行に潜り込んでいた

**なぜ機械が見逃したか。** `review` が見ていたのは、タイトルの文字数・概要欄の
文字数・タグ数・出力ファイルの有無・字幕の時刻の整合・尺だった。
**どれも「読めるか」を見ていない。** 文字数が上限内でも、行の割れ方は別の話。

同じ日に、画像のライセンス判定でも同じ構図が出た。`check_licenses.py` は
6枚すべて OK を返したが、目視すると4枚が使えなかった（被写体がスタジアムでなく
崖 / 彫刻が写っている・フランスにはパノラマの自由が無い / クラブ掲示とメーカー
ロゴが主役級）。**ライセンスは写真の著作権しか見ていない。**

### 一般形

自動チェックは「作った人が想定した壊れ方」しか見ない。
想定の外にある壊れ方は、**成果物そのものを見るまで分からない。**

- 画像・動画 → コンタクトシートやフレームを書き出して**開いて見る**
- 生成した文書 → レンダリング結果を読む
- API・データ → 実際のレスポンスを1件、目で読む
- UI → スクリーンショットを撮る

自分のPJTの点検が「何を見て、何を見ていないか」を一度書き出すと、
穴の見当がつく。上の例では「文字数は見ているが、行の割れ方は見ていない」だった。

## 巡回ログと時刻の読み方（2026-09-03 実例）

`docs/patrol-log.md` の行は、**書かれた時点の事実であって現況ではない。**
巡回は2時間おきなので、最新行でも最大2時間古い。巡回が止まっていればもっと古い
（実際 2026-09-03 は 11:20 の行から9時間空いた）。**現況を語る前に、CI と master を
実際に見る。**

### gh / git の時刻は UTC。JST は +9

これを取り違えると、原因と結果が入れ替わる。実際に起きた誤りを残しておく。

「patrol-log の 11:20 の報告以降、**11:32 の master 実行で success** だったので、
赤はその後の修正で自然に解消していた」という報告が出た。しかし
`2026-09-03T11:32:09Z` は **20:32 JST** で、9時間後の別のマージだった。

`gh run list --json createdAt` も `git log` の既定表示も UTC の `Z` 付きで返る。
`11:32` の数字だけを見て JST と読むと、**赤の前に起きた出来事に見えてしまう。**

実際の経過を一次情報で並べるとこうなる。

| JST | UTC | 出来事 |
|---|---|---|
| 10:49 | 01:49Z | perf-audit のマージで CI failure。master が赤くなる |
| 11:20 | — | 巡回ログに「master の soccer CI が赤」と記録（**この行は正しい**） |
| 12:58 | 03:58Z | PR #39 のマージで success。赤が解消（約2時間9分） |
| 20:32 | 11:32Z | PR #41 のマージで success（赤とは無関係） |

つまり赤を直したのは PR #39 であって、「自然に解消していた」わけではない。
巡回ログの行も古くなってはおらず、**間違っていたのは時刻の読み方だけ**だった。

### 他セッションの「もう直っている」も一次情報で確かめる

上の誤りは、受け取った側（当時の調整役）が確認せずに受け入れ、
「ログの最終行を鵜呑みにすると外す」という**誤った教訓を記録しかけた**。
ログは正しかったのに、ログのせいにするところだった。

報告が状態を語っているとき（直った・緑になった・もう無い）は、`gh run list` を
自分で叩いてから受け入れる。1コマンドで済む。相手を疑う話ではなく、
**2人が同じ思い込みを共有すると、それが記録として固定される**という話。

## Windows で日本語を出すスクリプトの stdout 差し替えは2系統ある（2026-09-03 実例）

CP932 のコンソールに `Perú` の `ú` を出そうとすると UnicodeEncodeError で落ちる。
対処は master に2系統あり、**置く場所が違う**。混在しているので、真似する前に
どちらの系統かを見分ける。

| 系統 | 置く場所 | 実例 |
|---|---|---|
| **A. `sys.stdout` を直接差し替える** | `if __name__ == "__main__":` ブロック | `projects/{ai-side-business,ir-analysis,quality-gainer-tracker}/main.py` |
| **B. 付け替える関数を呼ぶ**（`reconfigure`） | `main()` 冒頭 | `platform/ai-lab/src/browser/control.py`、`src/docparse/cli.py`、`projects/youtube-video-creation/src/cli.py` |

**A を main() の中に置いてはいけない。** `sys.stdout = io.TextIOWrapper(...)` は
pytest の出力捕捉を壊すので、main() を通るテストが書けなくなる（3件の main.py に
その理由がコメントで書いてある）。

**B は main() 冒頭でよい。** `reconfigure` は既存のストリームを付け替えるだけで
差し替えないため、捕捉を壊さない。

### どちらにするか

**そのスクリプトを import して `main()` を呼ぶテストがあるか**で決める。

- ある → B（関数形）。テストを壊さない
- ない → どちらでもよい。周りに合わせる

迷ったら B。実際に 2026-09-03、video-edit スキルの2スクリプトを直すときに
「A の形にせよ」という指示を受けたが、master の既存3件はいずれも B だった。
**根拠とされた FAQ の記載も存在しなかった。** 確認したところ A の3件は別の
場所（各PJTの main.py）にあり、系統が違うだけだった。
**指示された形が既存と逆に見えたら、実物を確認してから従う。**

## 同じ結論でも、方針なのか実測の制約なのかを書き分ける（2026-09-04 実例）

youtube PJT の CLAUDE.md「動画の型（変えないこと）」に、こう書いてあった。

> - 画面に立ち絵は出さない（報道番組の画面に寄せる）

ユーザーの決定で掛け合いに変えたとき、**立ち絵は結果的に出さないままだった。**
ここで「変わっていないから触らなくてよい」と判断しかけたが、
**理由がすっかり別のものになっていた。**

| | 立ち絵を出さない理由 |
|---|---|
| 変更前 | 報道番組の画面に寄せる（**方針**） |
| 変更後 | 仮素材が巨大で移籍カードに重なり、選手名が読めない（**実測の制約**） |

結論は同じでも、次に触る人の判断はまるで変わる。

- **方針**として書いてあれば、覆してはいけない
- **実測の制約**として書いてあれば、**前提が変われば覆してよい**
  （この場合は「立ち絵に足る素材を用意できたら」）

そこで方針としてではなく実測として書き直し、「素材を用意できたら改めて
検討してよい」と添えた。

### 一般形

**結論だけを保存すると、守るべきものと、事情で今そうなっているだけのものが
区別できなくなる。** どちらも同じ「〜しない」という文になるので、後から
読んでも見分けられない。

文書に「〜しない」「〜する」と書くときは、根拠がどちらかを一緒に残す。

| 根拠 | 書き方 | 次の人がしてよいこと |
|---|---|---|
| 方針・設計判断 | なぜそう決めたかを書く | 覆さない。覆すなら決めた人に確認する |
| 実測の制約 | **何を測ってそうなったか**を書く | 前提が変わったか確かめて、変わっていれば覆す |
| 外部の事情 | 何が起きているかと、いつ確かめたかを書く | 現状を測り直してから判断する |

**判断に迷ったら「これは何が変われば覆せるか」を自問する。** 答えが出るなら
制約であって方針ではない。その「何が変われば」を書き残す。

逆に、覆せる条件が思いつかないなら方針。**なぜそう決めたか**を書く。
理由の無い方針は、次の人が守る根拠を持てないので、いずれ破られる。

## テストはクラウドで回す（2026-09-02 方針）

**テストの実行はローカルではなく CI で行う。**ユーザーの決定。

### 根拠（soccer-manager での実測）

並行セッションが15ある状態では、このマシン(i7-10710U、6コア、空きメモリ
3.9GB/15.8GB)は競合しきっている。

| | 所要 |
|---|---|
| ローカル・フルスイート | 8分43秒（通常 2分40秒 = 3.3倍に劣化） |
| ローカル・game_logic_test.dart 単体 | 566秒 |
| **CI（同じコミット）** | **4分50秒 で success** |

**クラウドの方が速く、しかも安定している。**「ローカルで速く回して CI で最終
確認」という通常の前提が、この環境では逆転している。

ローカルの遅さが自分の変更のせいでないことは、変更のない master を別 worktree
に切って同じファイルを計測して確かめた(587秒。自分のブランチ566秒より遅い)。
ローカルが遅いときは、まずこの切り分けをしてから環境のせいにすること。

### 対象を絞って回す

全件を待たずに1ファイルだけ回したいときは、`soccer-ci.yml` を
workflow_dispatch で手動起動する。

```bash
gh workflow run soccer-ci.yml --ref <branch>   -f target=test/game_logic_test.dart -f skip_analyze=true
```

- `target` 空 = 従来どおり全件。指定は `test/` 配下のみ許可(それ以外は失敗する)
- `skip_analyze` は反復中だけ使う。push / PR では analyze は常に走る

### ローカルに残すもの

- `flutter analyze` はローカルでよい(80秒程度)
- ただし**通過条件は CI のテスト**。analyze は当てにならない場面がある
  （09-01 の節を参照。No issues found を返したのにコンパイルが落ちた）
