# 情報源として使えるサイト（実測）

WebSearch 経由でのアクセス可否を実際に試した結果。
**記事の本文はどのサイトも読めない**（見出しとスニペットのみ）ので、
本文が必要なときは人が読んで貼るしかない。

## 情報源の網（最終確認 2026-08-30）

すべて実際に検索して確認したもの。`config/sources.yaml` の `domains` に群ごとに分けてある。
**群ごとに「置ける確度の上限」が決まっていて、`draft` が突き合わせる。**

```bash
python -m src.cli sources     # 網の全体と、群ごとの確度の上限を表示
```

噂まとめだけを根拠に「確定」と出すと視聴者に対して嘘になるので、`draft` が止めます。

```
ヒント: 節『残された時間』: 確度『確定』に対して出典が弱いです
（いちばん強いもので english 群 = 報道 まで）。確度を下げるか、より強い出典を足してください
```

取得できないサイトを出典に入れると、これも警告が出ます。裏を取り直せないためです。

```
ヒント: 節『…』: 取得できないサイトを出典にしています（https://www.bbc.com/…）。
裏を取り直せないので、別の出典に替えてください
```

### クラブ公式が引ける

クラブ・リーグの公式サイトは検索でき、**声明そのものを引けます**。報道の又聞きではなく
一次情報になるので、`確定` として出せるのはここだけです。

```
en.atleticodemadrid.com/noticias/unanimous-support-from-the-board-of-directors-...
premierleague.com/en/news/4664145/when-does-summer-2026-...-open-and-close
jleague.jp/j1/special/transfer/            ← Jリーグの移籍まとめ（公式）
urawa-reds.co.jp/topteamtopics/242808/     ← クラブの移籍発表
```

**深掘りの検索でも、まず公式を当たります。** `pick` が出す検索リストの先頭近くに
「公式発表」が入っているので、声明が取れれば `確定` として出せます。
日本の公式サイトを引く検索は、`league: japan` の候補のときだけ出ます
（jleague.jp でアルバレスを検索しても意味がないため）。

### 現地語で引くと、英語では出ないものが出る

**いちばん効いた発見です。** ブンデスリーガの移籍を日本語・英語で探しても出てこなかったのに、
ドイツ語で引くと出てきました。しかも**リーグ公式**（＝`確定`）です。

```
検索: "Transfer offiziell Wechsel"  （kicker.de, sport1.de に限定）
      "official statement OR announcement transfer"  （bundesliga.com ほか公式に限定）

→ bundesliga.com  ボルシアMGが橋岡大樹を獲得（スラビア・プラハからレンタル）
→ bundesliga.com  マインツが川崎颯太の完全移籍を発表
→ sport1.de       RBライプツィヒが山本理仁と2031年まで契約
```

同じ日に日本語サイト・英語サイトを引いても、この4件は1件も出ませんでした。
**現地の話は現地語がいちばん速く、公式に辿り着きやすい。**
スキャンには各国語の検索を入れてあります。

### リーグを書くと現地語の検索が出る

サイトを増やすだけでは使えません。kicker をドイツ語以外で引いても何も返らないからです。
候補に `league` を書くと、そのリーグの言語の検索だけが出ます。

```yaml
  - id: alvarez
    league: spain      # → スペイン語の検索だけが出る
  - id: sano
    league: germany    # → ドイツ語の検索だけが出る
  - id: jleague_move
    league: japan      # → 日本の公式（jleague.jp ほか）を引く検索が出る
```

書けるのは `england` / `spain` / `germany` / `italy` / `france` / `netherlands` / `japan`。
書かなければ現地語の検索は出ません。

### 網が古くなったら

`config/sources.yaml` の `verified_on` に最終確認日が入っています。
90日を過ぎると `sources` コマンドが再確認を促します。塞がれたサイトも、
開いたサイトもあるので、各群に1本ずつ検索をかけて確かめてください。

## 日本語サイトは「日付」で引かない

これが最大の落とし穴でした。同じ日に両方を試した結果:

| 検索 | 結果 |
|---|---|
| `海外サッカー ニュース 2026年8月30日` | **一覧ページばかり**。個別記事ゼロ |
| `アルバレス アトレティコ 移籍` | 個別記事が10件。うち9件が当日〜3日以内 |

**日付を入れると一覧ページが返り、話題の語を入れると記事が返ります。**
英語サイトでは日付が効くので、つい同じ書き方をしてしまいますが、日本語では効きません。

`scan` の日本語クエリは、選手名・クラブ名・動詞（発表 / 交渉 / 移籍）で組んであります。

## 検索ツールの要約は信用しない

検索結果には「AIが生成した要約」が付くが、**見出しに存在しない内容を混ぜてくる**。
実際に踏んだ例:

- 移籍先が検索ごとに食い違った（同じ選手に別クラブが割り当てられた）
- 何年も前から在籍している選手を「今夏の新加入」として挙げた
- 2025年の投稿と2026年の投稿を混ぜて「今月の移籍」として並べた
- 返ってきた見出しのどこにも無い移籍（選手名・クラブ名ごと）を要約だけで断言した

**採用してよいのは、実際の記事見出し・投稿本文に書かれていることだけ。**
要約にしか出てこない情報は、別の検索で見出しレベルの裏が取れるまで使わない。

## RSSフィード（運用PCでいちばん速い経路）

検索経由には構造的な限界があります。索引が数時間〜2日遅れ、日付で引くと
一覧ページが返り、要約は捏造します。**RSSはサイトが自分で出している一覧**なので、
見出し・URL・正確な時刻が数分遅れで取れます。

```bash
python -m src.cli fetch --check                # 全フィードの生死を確かめる（最初に1回）
python -m src.cli fetch --hours 12            # 12時間以内の見出しを取る
python -m src.cli fetch | python -m src.cli collect   # そのまま候補ファイルに
```

### 索引の水準が自動で較正される

フィードは記事URLと**正確な公開時刻**を一緒にくれます。
「その記事IDが、いつの時点のものか」が推定ではなく分かるので、
`fetch` を回すと `research/freshness.yaml` の水準を較正します。

```
索引の水準を較正しました: skysports.com / kicker.de
```

1本のフィードには新旧の記事が入っているので、離れた2点が取れれば
**その1回で伸びの速さが出ます**（1点ずつ日をまたいで待たなくてよい）。
較正した記録が2つ以上あるサイトでは、そちらだけを使います。
`fresh` が記録する「見た時刻」は公開より遅いぶん、混ぜると
伸びを実際より遅く見積もるためです。

URLに日付が入るサイト（サッカーキングなど）と x.com は較正しません。
もともと日付が直接読めるので、水準を持つ意味がありません。

`fetch` の出力は「見出し<タブ>URL<タブ>経過時間」で、**そのまま `collect` に
流せます**。フィードの正確な時刻が候補の `hours_ago` に乗るので、URLから日付が
読めないサイト（Sky など）でも鮮度を捨てずに済みます。

**注意が2つ。**

- **開発環境からは届きません**（プロキシが403）。これは運用するPC用の経路です
- 設定に入っているフィードURLは**まだ実測できていません**。運用PCで
  `fetch --check` を回し、生きたものだけ `verified: true` に直してください。
  `doctor` が未確認のまま残っていると知らせます

経路の使い分け:

| 経路 | 速さ | 取れるもの | 使いどころ |
|---|---|---|---|
| RSS（運用PCのみ） | 数分遅れ | 見出し＋正確な時刻 | 朝のスキャン、速報 |
| 検索 | 数時間〜2日遅れ | 見出し | 深掘り、裏取り、公式へ辿る |
| X API（有料） | 遅れなし | 投稿全文 | 記者の一次発言 |

## 「最新かどうか」をどう判定するか

記事の本文は開けないので、**公開日はどこにも書いていない**。それでも新しさは判定できる。

### 記録・数字は統計サイトから

「数字で見ると」の節のために、統計サイトを群として分けてあります。
深掘りの検索リストに「数字（成績）」が入るので、得点・アシスト・出場数・
順位はここから取れます。移籍金は報道機関、成績は統計サイト、という分担です。

```
数字（移籍金・記録）: "... fee OR record"        （skysports.com ほか）
数字（成績）:         "... stats goals assists"  （fbref.com, understat.com ほか）
```

### 日本語サイトはURLに日付が入る（推定不要）

いちばん確かな手がかりです。推定ではなく**日付そのもの**が読めます。

```
soccer-king.jp/news/world/esp/20260828/2197673.html   → 2026-08-28
footballchannel.jp/2026/08/29/post1000500/            → 2026-08-29
caughtoffside.com/2026/08/29/julian-alvarez-arsenal/  → 2026-08-29
acmilan.com/en/news/articles/media/2026-01-30/...     → 2026-01-30
```

**登録していないサイトでも読めます。** URLに `/2026/08/30/` の形が入っていれば、
どのサイトでも日付を取ります（WordPress系に多い形）。日付として成立しない
ものは弾くので、記事IDを日付と誤読することはありません。

`fresh` はこれを「確定」と表示します。時刻までは分からないので、その日の正午に
出たものとして扱っています（半日ぶんの誤差はありますが、日付は確かめてあります）。

### ニュースサイト：記事IDが時系列に増える

URLに入っている記事IDは連番で、時系列に増える。アルバレスの件で確認した:

```
skysports.com/football/news/11095/13576511/  ブーイングは移籍の後押しか
skysports.com/football/news/11095/13576975/  アトレティコは態度を崩さず
skysports.com/football/news/11095/13577412/  「可能性はゼロパーセント」
skysports.com/football/news/11670/13577751/  バルサには売らない
skysports.com/football/news/11095/13578318/  本人に決断の期限
```

話が進んだ順とIDの順が一致している。**同じサイトの中でなら、IDが大きいほうが新しい。**

```bash
python -m src.cli fresh <URL> <URL> ...
```

サイトごとに新しい順で並べ、その日いちばん大きかったIDを
`research/freshness.yaml` に記録する。対応しているのは skysports.com と
espn.com と x.com。goal.com などIDがハッシュのサイトは判定できない。

### 前のシーズンの記事に気づける

日付や節で検索すると、**同じ見出しの前シーズンの記事**が返ることがあります。
見出しだけでは気づけません。実際に踏んだ例:

```
検索: "Premier League Gameweek 2 report goals winner"
→ premierleague.com/en/news/4391799/who-was-the-best-player-of-matchweek-2
   これは前シーズンの第2節。記事IDが 4,391,799 で、当時の最大 4,698,606 より
   30万以上も下だった
```

`fresh` は記録した最大IDと比べて、大きく下回るURLを知らせます。

```
! 前のシーズンの記事かもしれません: premierleague.com/en/news/4391799/…
    記事ID 4391799 は、記録している最大 4698606 を大きく下回っています。
    見出しが同じでも別の年の試合のことがあります
```

### 索引が止まっていたら分かる

記録があると、**前回から索引が進んだかどうか**が出る。

```
! skysports.com: 前回（08/29 06:00／24時間前）からいちばん新しい記事が
  変わっていません。検索の索引が進んでいないので、この結果は速報には使えません
```

これが出た日は、朝の速報枠をあきらめて深掘り側に切り替える。
**古い記事を「最新」として出すより、その日は速報を出さないほうがよい。**

### 何時間前かの推定

記録が2点以上たまり、12時間以上あいていれば、IDの増加ペースが出せる。
そこから「この記事は何時間前か」を推定する。

```
■ skysports.com　新しい順に3件　（記事IDの伸び: 370/時）
  13578352　6時間前（推定）
  13578318　8時間前（推定）
  13546220　87時間前（推定）
```

**ペースが出せないうちは「不明」と出す。** 記録が1点しかない状態で
それらしい数字を出すと、確認していないものを確認したことにしてしまう。

数字は「概算」で、**並び順だけが正確**。記事の出る量は時間帯で変わる
（夜間は少ない）ので、朝の数時間だけ観測したペースで前日を割り出すとずれる。
観測が24時間に満たないうちは、その旨が表示される。

```
※ 観測がまだ5時間ぶんです。記事の出る量は時間帯で変わるので、
  数時間より前の概算はずれます。並び順は正確です
```

記録が何日ぶんかたまると、昼夜がならされて精度が上がる。
観測した時間の3倍より前は、外挿になるので「不明」を返す。

候補ファイルの `hours_ago` は空でよい。`url` を書いておけば `pick` が割り出す。
割り出せなければ99時間（＝古い扱い）になり、その旨が表示される。

## X（旧Twitter）の集め方

x.com のページは開けない（egress で塞がれている）。取れるのは**検索結果のタイトル**だけで、
そこに投稿本文がそのまま入っている。

```
Fabrizio Romano on X: "🚨🔵🔴 Understand Alejandro Balde has informed
Barcelona about his desire to STAY at the club..." / X
→ https://x.com/FabrizioRomano/status/2092546263447146991
```

### 投稿日はURLから分かる

検索結果に投稿日は出ないが、**投稿URLの数字に時刻が埋まっている**（Snowflake ID）。
ページを開かずに投稿時刻を出せる。

```bash
python -m src.cli x https://x.com/FabrizioRomano/status/2092546263447146991
```

```
@FabrizioRomano　Fabrizio Romano（未確認）
    投稿: 2026-08-26 09:34 UTC　（79時間前）
    ! @FabrizioRomano の投稿は 79時間前のものです（24時間を超過）
```

これで「2025年の投稿が最新として混ざる」問題が消える。候補ファイルの `hours_ago` も
この数字を使う。`draft` のときにも自動で見て、古い投稿を出典にしていれば警告が出る。

**記事の日付は分からないが、Xの投稿日は分かる。** ニュースサイトは本文を開けないので
公開日を確認できない。日付を機械的に確認できるのはXだけ。

### Xは速報には使えない（実測）

検索の索引が追いついておらず、**いちばん新しい投稿でも1〜2日前**になる。
2026年8月30日に複数の検索で確認した結果:

| 検索 | いちばん新しかった投稿 |
|---|---|
| `Julian Alvarez Atletico Arsenal deadline` | 41時間前 |
| `transfer news confirmed medical signing` | 88時間前 |
| `Fabrizio Romano here we go August 30 2026` | **2025年の投稿**（日付を指定しても効かない） |

日付を検索語に入れても効きません。したがって:

- **速報（朝の枠）にXは使わない。** ニュースサイトの見出しで拾う
- Xが向くのは**背景・反応・裏取り**。「この話はいつから続いているか」
  「ファンがどう受け止めたか」は1〜2日前の投稿でも十分に使える
- 72時間より古い投稿を出典にするときは、**その後に続報が出ていないか**を
  ニュースサイト側で確認してから使う（`draft` が警告を出す）

### なりすましに注意

検索結果に**そっくりのハンドルが混ざる**。実際に出てきた例:

```
x.com/FabrizioRomano   ← 本物
x.com/fabrizioromab0   ← 別人
x.com/fabrizio1romao   ← 別人
x.com/fabrizio0romano  ← 別人
```

表示名は本物と同じ「Fabrizio Romano」です。**URLのハンドルを1文字ずつ確認する。**
`accounts` に登録したハンドルと完全一致しなければ `python -m src.cli x` が
「未登録」と出すので、そこで気づけます。

### 追うアカウント

`config/sources.yaml` の `accounts` に登録する。検索リストは `python -m src.cli x` で出る。
**ここに無いアカウントの投稿は `未確認` より上に上げない。**

| アカウント | 置ける最大の確度 | 何に強いか |
|---|---|---|
| @FabrizioRomano | `未確認` | 移籍全般。完了案件は here we go |
| @David_Ornstein | `未確認` | プレミア・The Athletic |
| @MatteMoretto | `未確認` | スペイン・イタリア |
| @DiMarzio | `未確認` | セリエA |
| @TheAthleticFC | `報道` | 媒体の公式アカウント |

ファンアカウント（@afcstuff、@ArsenalRadar など）は検索によく出ますが、
多くは記者の投稿を転載したものです。**転載を出典にせず、元の投稿を探す。**

記者個人の投稿は、どれだけ実績があっても**それ単独では `未確認`**。
主要紙が同じ内容を報じて初めて `報道` に上がる。
クラブ・リーグ・選手の公式アカウントは `確定`。
ファンアカウントとアグリゲーターは使わない。

### X API を使う（有料・遅れなし）

上の3つの弱点は、X API v2 から取れば全部消える。

| | 検索経由（既定・無料） | API（有料） |
|---|---|---|
| 鮮度 | **1〜2日遅れ** | 遅れなし |
| 本文 | **途中で切れることがある** | 丸ごと取れる |
| なりすまし | **混ざる** | `from:` で著者を限定するので入らない |
| 投稿時刻 | URLから逆算 | APIが返す |
| 費用 | 0円 | かかる（下記） |

```bash
export X_BEARER_TOKEN='...'          # トークンはファイルに書かない
```

```yaml
# config/sources.yaml
social:
  backend: api        # search から api に変える
  api:
    max_results: 10   # 1回に取る件数。読み取りは課金対象なので絞る
```

```bash
python -m src.cli x                    # accounts の投稿を新しい順に

```

`accounts` に登録したハンドルを `from:` で並べて検索するので、
**なりすましは最初から結果に入りません**。リツイートも除外します。

### 費用について（要確認）

**契約する前に必ず [docs.x.com/x-api](https://docs.x.com/x-api/getting-started/pricing)
で自分で確認してください。** この環境からは developer.x.com も docs.x.com も開けず、
検索結果の要約は当てにならないため（このドキュメントの上のほうを参照）、
ここに金額を書くと嘘になる可能性があります。

確認すべき点:

- **無料枠で他人の投稿を読めるか。** 読めないプランがあります。読めなければ課金が必須
- **読み取り1件あたりの単価と、月の上限**
- 1日3本の運用なら、1日に読むのは50〜100件程度。そこから月額を見積もる

金額を見て割に合わないと判断したら、`backend: search` に戻せば無料のまま動きます。
**APIが無くてもパイプラインは完結します。** 速報をXに頼らず、
ニュースサイトの見出しで拾う運用（いまの既定）で回せます。

### 切れた投稿は補わない

検索結果のタイトルは途中で切れることがある。

```
"...So far, Julian only wanted Barcel..."
```

**切れたまま引用するか、使わないかのどちらか。** 続きを推測で補わない。
`from_search_result()` は末尾が `…` `...` のものに印を付ける。

金額はアカウントごとに数字が違うことが多い。断定せず幅で伝える。

## 翻訳して使うときの線引き

- **事実そのもの**（誰がどこへ、いつ、いくら、誰が何と発言したか）に著作権はない。
  自分の言葉で書き直して伝えるぶんには問題ない
- **記事の文章をそのまま訳して流すのは避ける**。全訳は複製にあたる
- 発言やSNS投稿を引用するときは、出典を明示し、必要な長さに留め、
  引用が本編の主役にならないようにする
- 出典URLは `sources:` に入れれば概要欄に自動で載る
