# 成長ループの設計

## 解きたかった問題

プロジェクトが増えると、こういう状態になる。

- どのPJTに何が足りないか、頭の中にしか無い
- あるPJTで良い形にできても、他のPJTには伝わらない（毎回ゼロから同じことをやる）
- 改善したいことに気づいても、依頼文を書くのが面倒で後回しになる
- 動かなくなったことに、しばらく気づかない

どれも「気づき」ではなく「伝達」の問題。
だから作ったのは分析ツールではなく、**向こうから伝えてくる仕組み**にした。

## 設計上の判断

### 1. 指摘ではなく、着手できる形で渡す

提案には必ず「Claude にそのまま貼れる依頼文」を付ける。
「テストが無い」と言われても、そこから依頼文を考える手間が残るなら意味がない。
コピペで着手できるところまでを出力に含める。

### 1.5. 「作業」と「決めごと」を混ぜない

ライセンスの選定や「このPJTを続けるか」は、持ち主にしか決められない。
これを作業リストに混ぜると、片付かない項目が毎回上位に居座り、
リスト全体が読まれなくなる。`decision=True` を付けたルールは別枠に出す。

### 2. 少数に絞る

1PJTあたり最大3件、全体で最大12件。上限は `growth/projects.toml` で変えられる。

28件の指摘を並べるのは簡単だが、並べた瞬間に誰も読まなくなる。
溢れたぶんは捨てずに次回へ回す（ダイジェストの「見送った分」に出る）。

例外は `critical`（秘密情報の漏洩など）だけ。これは上限を無視して必ず出す。
漏らすと意味がない種類なので。

### 3. 根拠のある横展開だけをする

「テストを書くべき」は一般論だが、
「PJT003 では既に書いていて、その形をそのまま持ってこられる」は具体的な手順になる。

だから横展開ルールは、**その習慣を既に実践しているPJTが1つ以上ある場合にしか発火しない**。
お手本が無い習慣について説教はしない。
お手本には、その習慣を持っているPJTのうち最も規模の大きいものを選ぶ。

### 4. 記憶を持たせる

`growth/ledger.json` がこのシステムの記憶。指紋（fingerprint）は
ルールIDと対象プロジェクトだけから作るので、文面を推敲しても同一の提案として追跡できる。

| 状態 | 意味 | 次回の扱い |
|---|---|---|
| `open` | 未対応 | 再提示する（ただし回数が増えるほど静かになる） |
| `snoozed` | 見たうえで今はやらない | 理由つきで残すが、作業リストの枠は使わない |
| `resolved` | 指摘が消えた＝直った | 成果として数える。再発したら「退行」として報告 |
| `dismissed` | 人が「やらない」と判断した | 二度と出さない |

`snoozed` があるのは、「却下」と「今はできない」が別物だから。
環境が無くて検証できない、上流の方針待ち、といったものを `dismissed` にすると
状況が変わっても二度と戻ってこない。逆に `open` のまま置くと毎回上位を占める。

`dismissed` が増えたルールは信頼度が下がり、他PJTでも優先度が落ちる。
的外れな指摘を繰り返さないための学習にあたる部分。

### 5. しつこくしない

同じ提案を4回以上出しても着手されていない場合、優先度を回数に応じて下げる。
消しはしない（`status` には残る）が、他の提案を押しのけないようにする。

やらないことには理由があるはずで、催促を強めるより
`dismiss` で理由を書いてもらったほうが情報が残る。

### 6. 実行時の依存をゼロにする

`src/growth/` は標準ライブラリだけで動く。TOML は 3.11 の `tomllib`、
GitHub API は `urllib`、クローンは `git` コマンド。

定期実行するものに依存を積むと、自分は何も変えていないのに
ある日壊れる。点検する側が壊れていては話にならない。

### 7. 自分自身も対象にする

`ai-lab` も `growth/projects.toml` に登録してある。
このシステムが他PJTに要求していること（テスト、CI、定期実行の失敗通知、
依存の宣言）は、まず自分が満たしている必要がある。

`growth-loop.yml` の末尾に `if: failure()` で Issue を立てるステップがあるのは、
自分の `ci.silent-failure` ルールを自分で守るため。

## 成熟度スコア

0〜100。README / 実行手順 / テスト / CI / CIでのテスト実行 / .gitignore /
.env 除外 / 依存宣言 / CLAUDE.md / 秘密情報リスクなし、の重み付き合計。

絶対値そのものより、**時系列で上がっているか**を見るための数字。
`GROWTH.md` に推移がスパークラインで出る。

種別によって評価軸を変えている。

- 雛形だけのPJT → 中身が無い以上、点は伸びない（15点で頭打ち）
- モノレポの入れ物リポジトリ → テストや依存宣言は子PJT側の話なので評価しない

## 拡張のしかた

### 診断ルールを足す

`src/growth/rules.py` にデコレータで足す。

```python
@rule("docs.no-adr", kinds=("python",))
def _no_adr(snap):
    if snap.has("has_adr"):
        return None
    return _f(snap, "docs.no-adr",
              title="設計判断の記録が無い",
              why="なぜその形にしたのかが失われる。",
              action="docs/adr/0001-*.md を1本書く。",
              severity="low", category="docs", topic="adr")
```

`topic` を既存ルールと揃えると、横展開ルールと自動的に1件へマージされる。

### 横展開する習慣を足す

`practices.py` の `PRACTICES` にエントリを足す。`signal` は `survey.py` が出すシグナル名。
新しいシグナルが要るなら `survey.py` 側に追加する。

`requires_signal` を指定すると、その習慣がそもそも意味を持つPJTだけに絞れる。
たとえば `pinned-deps` は `requires_signal="has_requirements"` としてある。
依存を1つも持たないPJTに「バージョンを固定しろ」と言っても仕方がないため。
**適用条件を書き忘れると、対象外のPJTに的外れな指摘が出て、
システム全体が信用されなくなる。** ここは省略しない。

## 検出は2層になっている

最初の一巡で「無いもの」（README、テスト、CI、依存宣言）が片付いたあと、
同じルールを回しても何も出なくなる。そこで観点を足して次の層を見る。

| 層 | 見ているもの |
|---|---|
| 1層目 | 有無 -- README / テスト / CI / 依存宣言 / .env の扱い |
| 2層目 | 作り -- 例外の握りつぶし、ジョブの時間上限、トークン権限、長すぎる関数、BOM、存在しない参照 |

2層目を足すときの原則は、**誤検知を出さないこと**。
たとえば「握りつぶし」は当初 `except: pass` だけを見ていたが、
`except: continue` も同じだと分かって広げた。その一方で
`except (IndexError, ValueError): continue` は行スキップの意図表明なので、
種類を絞っている handler は対象から外している。

「一般論として正しい」だけの指摘は足さない。
1つ的外れが混ざると、正しい指摘まで読まれなくなる。

## 限界

- 観測はファイル構成と静的なパターンに基づく。コードの中身が正しいかは見ていない
- `hardcoded_secret_files` は正規表現なので誤検知しうる。だから提案文にも
  「ダミー値なら無視してよい」と書いてある
- Issue の起票先が他リポジトリの場合、既定の `GITHUB_TOKEN` では権限が足りない。
  `GROWTH_TOKEN` が要る
