# price-tracker — 楽天 値下がりウォッチ

楽天市場の価格を毎日記録し、履歴から値下がり・最安値圏を機械的に判定して公開する。
収益は楽天アフィリエイト。**価値は文章ではなく価格履歴の蓄積**（後から買えない資産）。

**楽天の値引きは価格ではなくポイント倍率で動く。** 実測（2026-09-10）では、価格が
5%以上下がった商品が17件だった日に、ポイント込みの実質価格では376件が下がっていた。
価格だけを見る実装では、その日の値引きを丸ごと取り逃す。

## 前提

- Python 3.12、**標準ライブラリのみ**。依存を足すときは `requirements.txt` に `==` で固定し、理由を書く。
- **実行時に生成AIを使わない**（費用と品質の両方の理由。README 参照）。
- 判定はすべて `src/analyze.py` の四則演算。根拠を後から説明できる形を保つ。
- `data/` は成果物ではなく資産。履歴なのでリポジトリに commit する。`dist/` は毎回作り直す生成物。

## よく使うコマンド

```bash
pytest                # テスト（ネットワーク不要）
python explore.py     # 対象ジャンルをデータで決めるための調査
python fetch.py       # 価格を取得して data/ に記録（要 RAKUTEN_APP_ID）
python build.py       # data/ から静的サイトを生成（通信しない）
```

## いまの運用（2026-09-05 に稼働開始）

- 取得は**手元PCのタスクスケジューラ `price-tracker-daily-fetch`**（毎日10:10、`run-daily.ps1`）。
  楽天は Backend Service 型で**許可IPからのリクエストしか受け付けない**ため、IPを固定できない
  GitHub Actions からは取得できない。**CI から取得する形に戻さない。**
- CI（`price-tracker-daily.yml`）は push された `data/` を検証し、ビルドして
  Cloudflare Pages へ公開する。あわせて鮮度を監視し、3日以上止まれば Issue を立てる。
- 公開URL: https://kakaku.dailyquarry.com（2026-09-25 に独自ドメインへ移した。
  `*.pages.dev` は Cloudflare 側の割り当てで、`price-tracker-bpe` という読めない名前だった）
- 対象ジャンルは8つ。**厚さ（取得件数）はジャンルごとに変える**（`config.json` の
  `genres[].hits`。無ければ `hits_per_genre`）。実測 2026-09-26 の配分は
  家電2,000 / TV・オーディオ1,700 / テレビゲーム1,500 / パソコン・周辺機器1,000 /
  残り4つ1,500。合計12,200件・408リクエスト・約7.5分。
- **どのジャンルを厚く追うかは `python genre_report.py` で決める。** 通信しない。
  値動きは履歴でしか測れないので、楽天に問い合わせる `explore.py` では出せない
  （explore は報酬額とレビュー数までしか見ない）。
  **記録7日未満のジャンルは「判定不可」と出る。** 追加した翌日に0%と出るのは
  動かないからではなく比べる相手が無いからで、それを見て切ると中身を見ずに
  捨てることになる（2026-09-26 に実際にそう見えた）。
  実測では家電が動いた28.5%・倍率>1が21.3%で最良、パソコン・周辺機器が
  17.2%・8.3%・中央価格1,980円で最下位だった。
- **同日リトライ**: 10:10 が失敗しても 14:10 / 18:10 に再実行する。当日ぶんが
  取れていればスキップする。失敗はその場でデスクトップ通知（IP変更なら現在のIP付き）。
  2026-09-23 の名前解決の失敗は、この仕組みで当日中に取り返した。
- 公開ページは約12,800枚。一覧は50件ごとのページ送り（最安値圏だけで4,000件近い）。
- **トップ（/）は案内だけのページ。商品を並べない**（2026-09-26 ユーザー指示）。
  検索窓・一覧の索引・ジャンルの入口・判定のやり方への導線を置く。
  点で並べた一覧は **`/now/`**。以前はこれがトップだったので、`/` を指していた
  リンク（ナビの先頭・空一覧の行き先・商品ページの `onward`）は全部 `/now/` を見る。

## 公開名義と連絡先

- 名義は**屋号「つるはし社」だけ**を出す（`config.json` の `owner`）。
  **個人名・ユーザー名を公開ページに出さない。**
- 連絡先は `info@dailyquarry.com`（`config.json` の `contact_email`）。
  Cloudflare の Email Routing（無料）で受けて個人のメールへ転送する。
  **転送先はリポジトリに書かない**（public なので受け側だけを置く）。
  kabu-agari-ranking と同じ窓口を共有している（転送規則を1本に保つため）。
- 公開URL は `https://kakaku.dailyquarry.com`（`config.json` の `base_url`）。
  canonical・OGP・robots.txt・sitemap が全部そこを見ている。

## 決まっていること（蒸し返さない）

- **アクセス解析ツールは入れない**（2026-09-26 ユーザー判断）。Search Console で
  検索の表示回数・クリック数が読めるので、判断にはそれで足りる。解析が足すのは
  「来たあとサイト内でどう動いたか」だけで、その差分のために第三者のスクリプトを
  足す値打ちが無い。`src/pages.py` のプライバシーポリシーに
  「独自のアクセス解析ツールを設置していません」と明記してあり、入れるとこの約束を
  書き換えることになる。無料であっても聞かずに入れない。

## 手を入れるときに気をつけること

- **保存の前に `src/validate.py` で検査している。閾値を緩めるときは理由を書く。**
  このPJTが依存しているのは自分のコードではなく楽天のAPIで、仕様変更は例外ではなく
  「0件」「空文字」といった静かな劣化として現れる（実際に4件踏んだ）。テストは全部
  モックなので CI は緑のまま通る。数で見て止めるのがここの役目。
  価格履歴は追記型の資産で、壊れた1日を混ぜると最安値・値下がりの判定が恒久的に歪む。
  1日欠ける方が損失は小さい。
- **`.ps1` は UTF-8 BOM 付きで保存する。** BOM が無いと PowerShell 5.1 が cp932 として
  読み、日本語の文字列リテラルが壊れて起動できなくなる（実際に `run-explore.ps1` で起きた）。
- `src/rakuten.py` は 1秒1回のレート制限を守っている。緩めない。
- `src/store.py` は同日に二度動かしても壊れない設計。この性質をテストで守っている。
- 秘密情報は `.env`（gitignore 済み）か GitHub Secrets へ。キー名は `.env.example` にある。
- **「動いたか」はポイント込みの実質価格で見る（`effective_change_count`）。**
  価格だけで数えると動いたのは1,486件（13.9%）だが、ポイントを含めると
  2,252件（21.0%）になる（実測 2026-09-26・記録2日以上の10,701件）。
  履歴は `[日付, 価格, 倍率]` で持っているので後から出せる。
  商品ページは倍率が動いた回だけ実質価格を破線で重ね、価格が横ばいでも
  実質が下がっていればその旨を注記に書く（図と文が食い違わないように）。
- **一覧を増やすときは `analyze` に判定を、`build.write_listing` に出力を足す。**
  件数上限は既定で無い。切るのは表示側の判断。
- **検索結果に出る文字列は `clean_name` を通す。** 楽天の商品名は先頭に
  「【9/25限定！抽選で最大100%P還元…】」のような宣伝が付き、題の28文字が
  それで埋まる。実測（12,593件）で 1,940件が記号か煽り始まり、1,531件は
  別商品なのに題が同じだった。宣伝は日替わりなので題も毎日変わる。
  落としてよいのは先頭だけで、名前の途中の「送料無料」は商品の情報。
  **囲み（【】[]）は中身を見てから落とす。** 中身を見ずに落としていたとき、
  「【松岡良治】【クラシックギター用弦セット】MC1000MT」が型番だけになっていた
  （33件）。落とすのは `PROMO_HINT` に当たる中身だけ。＼…／ は飾り自体が宣伝
  なので中身を見ない。**囲みの種類は【】[]［］『』「」（）〔〕《》≪≫ を全部見る**
  （【】と[]しか無く86件が素通りしていた）。開きと閉じの対は厳密に見ない。
  「［メール便OK]」のように全角と半角が混ざる名前が実在する。
  **「新品」「中古」「公式」「2個セット」「1年保証」は落とさない。**
  買う側が商品を見分けるのに使う。落としてよいのは配送とキャンペーンの言い回し。
  **下限は3文字**（6文字だと「白メダカ」まで戻していた）。
  正規表現の `|` は最長ではなく先に当たった方を採る。日時は細かい形を先に置く。
- **「似た商品」は名前の近さで選ぶ（`src/relate.py`）。** 同じジャンルの先頭から
  8件を取っていたとき、商品ページ60枚が33商品・5通りしか出していなかった。
  読み手には関係のない商品が並び、ページどうしのリンクもひと握りに集中して、
  残りは一覧のページ送りからしか辿れなかった。名前の近さにすると
  リンク先が 64 → 12,021種類に広がる（計算は5秒、ビルド全体で41秒）。
  ありふれた語（ケース・セットなど）は手がかりにしない。割合（8%）だけだと
  件数の少ない集合で語が全滅するので、下限（50件）も置いてある。
- **索引に載せるかは「どの一覧からも辿れるか」で決める（`linked`）。**
  記録日数で切ったら、ジャンルを足した翌日の 7,346件まで落ちた。
  一覧を足せば自動で追従するので、判定条件を書き足す必要はない。
- **構造化データに、持っていないものを書かない。** Search Console は推奨として
  aggregateRating・review・hasMerchantReturnPolicy・gtin・brand を求めてくる
  （2026-09-27 に通知）。いずれも**入れない**。レビューは楽天のもので当サイトは
  持たず画面にも出していない、返品条件は販売者ではないので知らない、型番と銘柄は
  APIが返さない。画面に出していないものを構造化データにだけ書くのは検索側への嘘で、
  Google の決まりにも反する。テストで固定してある。
  入れたのは `validFrom`（価格を記録した日）と `shippingDetails`（送料無料の回だけ。
  有料の回は金額を知らないので書かない）の2つだけ。
- **検索結果に出る印は `data:` で置かない（`src/icon.py`）。** ブラウザのタブには
  出るが、Google は**クロールできるURL**からしか印を拾わない。data: URI にして
  いたため、携帯の検索結果は3件とも地球儀の代替アイコンだった（2026-09-26 に
  ユーザーの画面で確認）。`icon.png`（192px＝48の倍数）と `favicon.ico` を
  ビルドで書き出している。画像ライブラリは使わず zlib と struct で組む
  （依存を足さない方針のため）。
- **サイト名は WebSite の構造化データで渡す（`site_ld`、トップだけ）。**
  渡していないと検索結果に「kakaku.dailyquarry.com」と生のドメインが出る。
- **JS は「取り出してから使う」。`var` の巻き上げは値を運ばない。** 一覧の道具で
  `var freeonly = document.getElementById(...)` を使うより後ろに書いていたため、
  `?free=1` 付きのURLを開くと `undefined.checked = true` で例外になり、
  **一覧の道具が丸ごと死んでいた**（並び替えも価格帯も「条件を外す」も効かない）。
  絞り込むと URL に `?free=1` が入るので、再読み込みや共有のたびに起きる。
  宣言だけは巻き上がるので構文は通り、テストもモックでは気づけない。
  **絞り込みを触ったら、そのURLを開き直してコンソールを見る**（2026-09-28 に発見）。
- **JavaScript も CSS と同じで、外に出して指紋を付ける。** `app.<8桁>.js`（全ページ・
  `head` で**同期**読み込み）と `list.<8桁>.js`（一覧だけ・`defer`）。全ページに
  直書きしていたとき、配信物は285MBで商品ページ1枚が21.1KBだった（→251MB・18.7KB）。
  **app.js は defer/async にしない。** 本文側が `PTWatch` を使うので、
  読み込みを遅らせると順序が変わって壊れる。逆に app.js の中で要素を触る処理は
  `DOMContentLoaded` を待つ（head で読む時点では要素がまだ無い）。
- **SVG の要素に `hidden` プロパティは無い**（HTML要素のもの）。JS で
  `el.hidden = false` と書いても何も起きず、目印が出たままになる。
  SVG の中で出し入れするものは**クラスと CSS**で切り替える（`.reading`）。
  2026-09-27 に図の読み取りを入れたとき実際に踏んだ。
- **検索の索引も指紋を付ける（`search-index.<8桁>.json`）。** 3.9MB
  （圧縮後1.1MB）あるのに名前が固定で、Cloudflare の指定が max-age=0 だった
  ため検索のたびに取り直していた。名前は `PT_INDEX` としてページ側へ渡す
  （検索と見守りの2枚）。`robots.txt` は前方一致（`Disallow: /search-index.`）で塞ぐ。
- **`src/style.css` を直したら、配信されているか名前で確かめる。**
  中身の指紋をファイル名に入れている（`style.<8桁>.css`）。以前は名前が
  固定で、`_headers` の max-age=3600 も Cloudflare 側に 14400 へ上書きされ、
  直した見た目が4時間届かなかった。
- **動いていない商品にも言えることを出す（`sub_position`）。** 実測
  （2026-10-03）で、記録している13,544商品のうち**9,700件（71.6%）は価格も
  実質価格も一度も動いていない**（価格だけ見ると2,680件=19.8%しか動かず、
  実質でも3,844件=28.4%）。その商品ページには「ずっと同じ値段」という情報しか
  無く、価格を追うサイトとして出せるものが何も無かった。
  **同じ分類の中での位置**なら動いていない商品にも言える（「アクセサリー・部品
  687件のうち安い方から325番目。この分類の価格は99円〜42,800円、真ん中は
  1,498円」）。13,544商品ぶんの価格を毎日持っているからこそ出せるもので、
  1商品だけを見ても分からない。真ん中より高い商品は「高い方から」で数える。
- **トップからの深さを測ってから直す。** 実測（2026-10-03・トップから幅優先で
  辿る）で、商品ページ13,465枚のうち **5,631枚（42%）が深さ4以上**にあった。
  中分類への入口を `/genre/` に集め、件数の多い中分類3つをトップにも出すと
  **2,970枚（22%）** まで減った（深さ2は588→1,479枚）。
  深さは「トップから何回押せば着くか」で、クロールが届く範囲に直結する。
  **階層を増やすと逆に深くなる**ので、増やすのではなく上から直接つなぐ。
- **中分類への入口は `/genre/` に集める。** ジャンルページの中にしか置いて
  いなかったとき、126枚の中分類はトップから2クリック先にあった。索引に集めると
  1段縮み、その奥の商品ページまでの深さも全部1段縮む。
  13,883ページあって検索の表示は544（2026-10-02）で、**ほとんどのページは
  検索に出ていない**。読み手が着けない場所にはクロールも届かない。
- **ページ送りは「奥に着けるか」で見る。** 近辺±2だけだと81ページある一覧の
  40ページ目まで20回押す。飛び先は5刻み（10刻みだと14〜18が1手多い。
  テストが見つけた）。読み手が着けない場所にはクロールも届かない。
- **一覧はすべて実質価格でも見る。** 判定を1つ実質に寄せたら、同じ考えで並ぶ
  一覧も揃える。実測（2026-09-28）で、日付別は 9/26 が52件→69件・9/27 が
  17件→29件、値上がりは45件→146件、最安値圏は245件→501件になった。
  片方だけ直すと、同じサイトの中で「安い」の定義が2つになる。
- **前回との比較には「前回より」を必ず添える。** すぐ下の「記録を始めてからの
  変化」は記録開始との比較なので、「変わらず」と「▲16.5%」が同じ画面に並ぶ。
  どちらが何との比較なのかを書かないと、読み手には食い違いに見える。
- **過ぎた日の一覧は `drops_on()` で当日の前日比を取り直す。** 「最後に価格が動いた日」
  で代用すると取りこぼす（2026-09-24 に実際にそうなっていて、9/20 が37件→1件だった）。
- **SVG の中の文字は、絵と一緒に縮む。** 価格の図は `viewBox="0 0 560 180"` を
  幅343pxの携帯に収めるので0.61倍になり、`font-size="11"` は実寸6.7pxだった。
  右端の日付は絵の枠（560）から出て切れていた。**目盛りは SVG の外に HTML で置く**
  （`.chart-tick` を `--gutter` の位置に、日付は `.chart-dates`）。
  読み取り欄を探す JS は `svg.closest('.chart-box')` から辿る（親が1枚増えた）。
- **1列のグリッドでも、中身が縮まないと列ごと画面の外へ伸びる。**
  `.cards` は `display: grid` の1列だが、列の下限が中身の最小幅になるため、
  店名の長い商品（「シャンパン専門店 CHAMPAGNE HOUSE」）があるページは
  幅360pxで最大29px はみ出していた。`grid-template-columns: minmax(0, 1fr)` を置く。
  **はみ出しの検査は幅320〜360も当てる。** 375だけだと4ページ見落とす。
- **枠が反応するのに押せるのが文字だけ、を作らない。** `.hits li`（日付別・記録）は
  触れると枠の色が変わるのに、押せるのは27pxの文字だけだった。
  一覧の行・ジャンル・カードは `a::after { position: absolute; inset: 0 }` で
  全体を押せるようにしてある。カードの中の「見守る」は `z-index: 1` で上に出す。
- **押しどころは36px以上に揃える。** 折り返した並びの**行と行の隙間**も見る。
  `.site-nav` は狭い画面で `gap: 0 12px` だったため、2行目のリンクが1行目と
  隙間0pxで接していた（「最安値圏」の下端＝「商品を探す」の上端）。
- **いま見ている一覧に印を付ける（`nav_html` の `aria-current`）。**
  どのページかは `head()` が受け取る `canonical` から出す（`_here`）。
  head の呼び出しは40か所以上あり、別引数で渡して回ると必ず渡し忘れが出る。
- **切り詰めた名前が同じになる並びを作らない（`distinct_short`）。** 名前の近さで
  似た商品を選ぶので、頭が同じで末尾だけ違う商品（枚数違い・色違い）が隣り合う。
  実測で、行き先の違うリンク3本が同じ文字になっていた。分かれる位置から先を足す。
- **索引は広い画面では面で並べる。** トップの一覧が縦1列で、幅1900pxでは右が
  まるごと空き、11項目が縦に伸びて一画面に収まらなかった（2026-09-28 に
  ユーザーが価格.com のトップと並べて指摘）。あちらは全カテゴリを3列のます目で
  出している。640pxで2列・1040pxで3列にし、**トップだけ本文幅を 860 → 1120px**
  に広げた（索引だけのページでカードも表も無いので崩れない。他のページは 860px
  のまま）。縦の長さは 2,909px → 1,616px になった。
  トップかどうかは `main.wrap:has(> .howto)` で見分ける（`head()` の呼び出しが
  40か所以上あるので引数を足さない。`:has()` が効かない環境では 860px のままで、
  それでも読める）。
- **ジャンルの下に「そのジャンルらしい語」を置く（`relate.genre_terms`）。**
  価格.com のトップはカテゴリの下にサブ項目を2行置いていて、それが面の情報量を
  作っている（「ノートパソコン タブレット ハードディスク PCパーツ 周辺機器」）。
  うちは楽天のジャンルを8つしか取っておらず下の階層を持たないので、**商品名から
  出す**。ただ数えるだけだとどのジャンルにもある語（セット・送料無料）が並ぶので、
  そのジャンルでの出現率を全体の出現率で割った値で選ぶ。語は検索への行き先にする
  （読むだけの飾りにしない）。0.4秒。
  **同じものの別表記を並べない。** 「ヤマハ」と「yamaha」、「スイッチ」と
  「switch」は読みの対応を辞書なしでは付けられないが、**文字種が違ううえ共起する**
  ことで見分けられる。文字種の条件を外すと、同じ商品群にしか出ない別のもの
  （「ヤマハ」と「電子ピアノ」）まで落ちる。
- **一覧の頭に、語での絞り込みを件数つきで置く（`term_chips`）。** 価格.com の
  カテゴリページは上のほうに「注目スペック」（おもに6畳用・自動掃除機能付き・
  窓用エアコン…）とメーカーを**件数つき**で並べていて、1,500件の中から1手で
  自分の探しているものへ入れる。うちのジャンルページは31ページのページ送りしか
  無く、奥へ行く道が「次へ」だけだった。件数は押す前の手応えになる
  （価格.com の「ダイキン(747)」と同じ）。
  **相対パスは組み立て済みの文字列で渡さない。** ページ送りの2枚目からは階層が
  1つ深くなるので、`../../` を外から渡すと 404 になる（2026-09-28 に踏んだ。
  `breadcrumb2` でも同じ所で踏んでいる）。データで渡して、出す側で `prefix` を
  付ける。**ページ送りの奥のページでリンクを実際に開いて確かめる。**
- **ジャンルの名前と階層は `data/genres.json` に控えてある（`fetch_genres.py`）。**
  楽天の商品検索APIは末端の `genreId` を返すが名前は返さない。ジャンル検索API
  （IchibaGenre/Search）は `genre`（名前・深さ）と `ancestors`（祖先すべて）を
  返すので、一度引けば以後は通信なしで使える。実測（2026-09-28）で商品は
  **1,054種類の末端ジャンル**に散らばっていた。1秒1回の制限があるので全部で18分。
  日々の取得では引かない（新しいIDが出たときだけ手で回す）。
  **末端のままでは大ジャンル1つに57〜202種類あって多すぎる。`level 2` でまとめる**
  （家電 → 季節・空調家電608 / 美容・健康家電479 / キッチン家電427…）。
  10件に満たない中分類はページを作らない（「電卓・デジタル文具1」まで並べると
  面が散らかる。そこにある商品は大ジャンルの一覧に出ているので辿れなくならない）。
- **`attributeIds` は属性の値を返さない。** 商品は `attributeIds` を持ち、
  ジャンルの属性定義には「ブランド名」「メーカー型番」があるが、返るのは
  **どの属性を持つかのIDだけ**で値は無い。メーカー名での絞り込みは作れない。
  ブランドらしい語は商品名から拾うしかない（`relate.genre_terms`）。
- **買える場所へは、価格を見た所から行けるようにする。** 商品ページの
  「楽天市場で見る」は下に1つだけで、スマホでは **2,848px（3.5画面ぶん）下**に
  あった。実測（2026-09-26〜29）で検索から5人来たあいだ、楽天へのクリックは
  **27から1つも動いていない**（ユーザーが管理画面で確認）。母数は小さいが、
  そもそも到達していない見込みが高い。価格の直後にも1つ置いた（658px＝1画面目）。
  **断り（`AD_NOTICE`）は買う口より先に出す。** 何で収益を得ているかを、
  押す前に読めるようにする。下の1つは残す（記録を読み終えた人向け）。
- **検索結果に並んだときの題と説明を、押す理由から書く。** 表示115に対し
  クリック5（4.3%）だった（2026-09-30 実測）。題は中央50字あり、日本語の
  検索結果は30〜40字で切られるので「の価格推移・最安値｜楽天 値下がりウォッチ」が
  まるごと見えていなかった。説明は「6日分の記録では価格は横ばいです」で終わって
  いて、押す理由が読めなかった。
  **商品ページの題にはサイト名を付けない**（商品名28字＋「の価格推移」で33字。
  サイト名11字を足すと、何のページなのかを言う部分まで切れる。ドメインは検索結果に
  別に出る）。**説明の頭は判定にする**（「記録した中でいちばん安い 438円 です
  （最高値から26.8%下がりました）」）。題は中央50→34字、説明は92→78字になった。
  一覧とトップにはサイト名を残す（枚数が少なく、名前を出す値打ちがある）。
- **値上げが記録された商品は、題を「◯◯の値上げ・価格推移」にする（`analyze.last_hike`）。**
  検索で「氷結無糖レモン 値上げ」が8.8位・表示46回なのにクリック0だった（2026-10-06）。
  探す人が知りたいのは「いつ・いくら」なので、説明と本文の頭に「この店の価格は10月1日に
  4,809円 → 4,954円（+145円・3.0%）に上がりました」と書く。**メーカーの改定額ではなく
  この店の楽天での価格**なので、そう書く。値上げと呼ぶ条件は、1回で2%以上・上がった先が
  記録上いちばん高い（セール終了で戻っただけを除く）・上がる前の記録が3日以上・
  上げ幅の半分以上が残っている。**9/12 までの上昇は数えない**（記録開始の 9/5 に
  スーパーセールが進んでいて、セール価格しか知らない商品と区別できない）。
  実測（2026-10-07）で841件、9/29〜10/3 の酒類の値上げが中心。
- **日本語の本文は1行40字までにする。** 幅1280pxで52〜64字になっていた
  （`.static p` に `max-width: 62em` が残っていた）。
- **「最安値」は、価格が動いたうえでの最安値に限る（`moved`）。** 動いていない商品は
  その値段が自動的に記録上の最安値になる。実測（2026-09-28・記録23日）で、
  「記録した中で最安」の札が付いていた3,925件のうち**3,701件（94.3%）が1円も
  動いていなかった**。安くなったわけではないのに札が付き、読み手は値下がりがあったと
  受け取る。条件に「記録のあいだに価格が動いたこと」を足して224件に絞った。
  動いていない商品は「変動なし」と表示し、最安値圏の一覧にも点（`score_breakdown` の
  「最安値への近さ」）にも入れない（入れていたとき `/now/` 600件の358件がこれだった）。
  **最安値圏は4,012件 → 245件に減る。看板の一覧が痩せるのは承知のうえ**（2026-09-28 指示）。
- **最安値はポイント込みの実質価格でも判定する（`eff_at_low`）。** 楽天の値引きは
  価格ではなく倍率で動くことが多いので、価格だけで見ると「いまがいちばん得」を
  取りこぼす。実測（2026-09-28・記録が7日以上ある5,074件）で、価格が記録した中で
  最安なのは224件だが、実質で見ると481件あり、**そのうち269件は価格では最安では
  なかった**（うち248件は価格が1円も動いていない）。最安値圏の一覧は
  245件 → 501件になる。
  **札は分ける。** 価格が最安なら「記録した中で最安」、価格は最安でないが実質が
  最安なら「ポイント込みで最安」。後者を「最安」とだけ書くと、同じページに出て
  いる価格の表と食い違って見える。色は価格の最安と同じ緑にし、**枠を破線**に
  する（図でも実質価格は破線で描いている。意味づけを揃える）。
  一文（`verdict_note`）は `moved` の分岐より**前**に置く。倍率だけが動いた
  商品は `moved` が偽なので、後ろに置くといちばん言うべきことが消える。
- **値上がりも実質価格で見る（`eff_rise_pct`）。** 倍率が下がる（期限切れを含む）と
  価格が同じでも実質は上がる。実測（2026-09-28・しきい値5%）で、価格が上がったのは
  45件だが実質では139件あり、**101件は価格では上がっていなかった**。
  「もう得ではない」は待っていた人にいちばん要る知らせで、価格しか見ない作りでは
  出せない。値上がりの一覧は 45件 → 146件。
  **`point_note` は倍率1で打ち切らない。** 倍率が1に戻った回こそ知らせるべき
  なのに、`rate <= 1` で空を返していたため一覧では何も変わって見えなかった。
  ただし**価格も上がった回は印を出さない**（同じ割合がカードの価格の行にも出て、
  「▲458.8%」が1枚に2回並んでいた）。
- **「最安値に近い」は、値幅がしきい値より大きい商品だけ（`spread_pct`）。**
  値幅そのものが2%以下だと、どの日を取っても最安値の2%以内に入る。実測で87件のうち
  66件がこれで、**そのうち50件はいまが記録上の最高値**なのに札が付いていた。
- **札の文言は「変動なし」と「前回から変わらず」を分ける。** 前者は記録のあいだずっと、
  後者は前回との比較だけ。以前は後者を「横ばい」と呼んでいて、見分けが付かなかった。
- **商品ページでは「どれだけ下がって最安に来たか」を添える。**
  最安値だと言うだけでは、値幅0.1%の商品と16.7%の商品が同じ顔になる。
  表にも「記録した中の値幅」を出す。
- **楽天の掲載文はそのまま載せない（`clean_caption`）。** 商品ページの「商品の説明」は
  楽天の文の冒頭200字だが、実測（2026-09-28）で12,750件のうち2,028件（15.9%）に
  「ぜひ」「オススメ」「超お買い得です」が入り、1,360件は
  「関連商品＼楽天1位獲得／…1,000円1,000円…」という**別商品の名前と値段の羅列**だった。
  出典を書いていても、読み手には当サイトが勧めているように映る。
  羅列と飾りは説明ごと出さず、煽りは文の単位で落とす。残りが30字未満なら出さない。
  結果は 12,750件 → 10,981件（86.1%）で、残った説明に煽り・羅列は0件。
- **名前の途中に残る宣伝も落とす（`strip_mid_promo`）。** 先頭だけ落としていたので、
  「SDカードリーダー **楽天ランキング1位** 大容量対応…」が題にも一覧にも出ていた
  （実測491件・3.7%）。落とすのは順位・セール・クーポン・累計・急かしなど、
  商品を見分けるのに使えないものだけ。**「送料無料」「新品」「2個セット」
  「1年保証」「公式」は残す**（この線引きは変えない）。
- **配布する CSV の名前も `clean_name` を通す。** 生の名前は先頭の宣伝が日替わりで
  書き換わるため、同じ商品でも日によって別の文字列になる。
- **404 は `noindex` にし、canonical を 404 自身にする。** トップを canonical に
  していたため、存在しないURLすべてが「トップと同じページ」だと申告される形だった。
  404 の中のリンクも `/` ではなく `/drops/` を指す（`/` は案内ページに変えてある）。
- **「この価格以下だったのは◯日（100%）」を出さない。** 全日が該当するのは
  「いまが記録上いちばん高い」ときで、100%と書くと安い日が多いように読める
  （実測1,035件）。そのときは「これより安かった日はありません」と書く。
- **読めなかった画像は枠に差し替える（app.js の `error` 捕捉）。**
  楽天のサムネイルは商品が消えると読めなくなり、壊れた絵の記号と40文字の
  代替文がカードの中で溢れる。`error` は泡立たないので捕捉の段階で受ける。
- **ヒアドキュメントに `\` を直接書かない。** この環境では
  `bash <<'PY'` の中でもバックスラッシュが潰れ、`\b` が実際の後退文字として
  ファイルに書き込まれた（正規表現が無言で当たらなくなる）。
  `B = chr(92)` を組み立てるか、置換用の記号を使って後から差し替える。
- **絞り込みで全部消えたら、そう書く。** 一覧の条件を絞って0件になったとき
  カードが消えるだけで何も出ず、ページが空白になって壊れたように見えていた。
  「条件を外す」への導線まで出す（`#nofit`）。
- **価格の記録の表に見出し行を置く。** 見出しが無く、3列目（ポイント倍率）は
  名前も中身も無い空のセルだった。読み上げでは「空白」としか言えない。
  **倍率は独立した列を持たせず、実質価格の下に小さく添える**（列を足すと
  幅320pxで表がはみ出す）。通常ポイント（1倍）は書かない。
- **画面の組み立ては価格.com の価格推移ページに倣う。** あちらは
  「図 → 参考情報（初値 / 現在 / 差額・値下がり率）→ 日別の価格変動（日付・
  最安価格・**変動額**）」の順で、いくらから・いくらまで・どの日に動いたかが
  金額を読み比べなくても追える。同じ並びを商品ページに入れた
  （`since_start` と `history_table` の前日差の列）。
  **ただし「初値」とは書かない。** うちが持っているのは記録を始めた日の値段で、
  発売時の値段ではない。持っていないものを持っているように書かない。
- **うちの強みは、価格が動かない日の値引きを拾えること。** 価格.com は価格しか
  見ないので、倍率だけが動いた回は「変動なし」になる。実測（2026-09-28）で
  `dentendo-10026508-15813ae1` は価格が1円も動かないまま実質が19.2%下がり、
  `aikyoku-10009635-a04132aa` は価格 −2,000円（10.6%）に対し実質 −3,492円
  （18.8%）だった。**価格.com に倣った表にも、必ず実質の行と列を並べる。**
  倍率が一度も付いていない商品では実質の行を出さない（価格の1%引きを並べる
  だけで、読み手に何も足さない）。
- **一覧のカードに出している情報は、商品ページにも出す。** 送料無料・あす楽・
  在庫切れ・ポイント倍率・実質価格は `card()` には出ていたのに、商品ページの
  頭には無かった。倍率が付いた商品では実質が19%も違うことがあり
  （`dentendo-10026508-15813ae1`）、いちばん大事な数字が頭に出ていない。
  **送料無料にいたっては構造化データにだけ書いていて、画面には出していなかった**
  （実測2026-09-28・先頭3,000枚のうち `shippingDetails` を書いた1,946枚の
  658枚（33.8%）で、本文のどこにも「送料無料」が無かった。残りは商品名に
  たまたま含まれていただけ）。画面に出していないものを検索側にだけ伝えるのは、
  こちらの決まりに反する（`shippingDetails` を入れたときの理由と食い違う）。
- **同じ商品を店ごとに横比較する形は作れない。** 価格.com の核心は
  「1商品 × 60店舗」の横比較だが、うちでできるのは名前が完全に一致する組を
  束ねることだけで、実測（2026-09-28・13,406件）では**140組・そのうち店が
  違うのは90組186件（1.4%）**しか無かった。楽天の商品名は店ごとに違い、
  束ねる鍵になる型番を API が返さないため。**再提案しない。**
- **価格の記録から古い日を捨てない。** 直近14日で切っていたが、記録の蓄積が
  このPJTの価値そのもので、23日ある記録の9日が読めなかった。全期間を1枚の表に
  書き、15行目から先を CSS で隠して印（`.allhist`）で開く。**表を2枚出さない**
  （13,406ページあるので配信物がその分ふくらむ）。JS は使わない
  （読み込む前でも開ける）。印刷では畳まず全部出す。
  **記録が伸びるほど1ページが厚くなる。** 2026-09-28 時点で商品ページ1枚
  20.0KB・配信物333MB。100日を超えたら上限を考える。
- **同じ数字を3か所に置かない。** 商品ページの表は9行のうち5行（現在の価格・
  前回の価格・倍率・実質価格・記録日数）が、上下の「記録を始めてからの変化」
  「価格の記録」と同じ数字だった。表に残すのは**記録した中でのいまの位置**
  （最安値・最高値・最安値との差・値幅）だけにし、題も付けた。
  記録が1日しかない商品は上下の表がどちらも出ないので、そのときだけ
  価格・倍率・実質価格をここに出す。
- **期限切れの補正は `tail` の最終日にも入れる。** `last_rate` だけ直していたため、
  頭の「実質 27,225円」と「価格の記録」の同じ日が 23,375円 で食い違っていた
  （図・「記録を始めてからの変化」・「価格の記録」はすべて `tail` から作る）。
  **画面の数字がどこから来ているかを確かめてから直す。**
- **期限が取得日より前の倍率は、倍率1として扱う（`evaluate_all`）。**
  楽天は期限切れの倍率を返してくる（実測2026-09-28に93件、うち63件は倍率>1）。
  そのまま出すと「ポイント2倍 / 実質13,710円」と、もう受け取れない値引きを
  見せることになる。`ending_soon` は元から期限切れを外していた。
- **見守りページは `noindex`（sitemap にも載せない）。** 中身は端末の中にしか
  無いので、検索から来た人には空のページしか見えない。
  JS が無い人向けに `<noscript>` の一言も置く（検索ページにも）。
- **楽天の画像置き場へ `preconnect` を張る。** 一覧1ページで別ドメインから
  50枚読むのに、接続の先取りをしていなかった。
- **同じものを2つの言い方で呼ばない。** 「ポイント込みの実質価格」と
  「ポイント分を引いた実質価格」が同じ商品ページに出ていた。図の凡例に揃える。
  「記録日数」と「記録した日数」も揃えた。
- **64文字まで伸ばしても題がぶつかる組は、店名で分ける（`page_titles`）。**
  同じ商品を複数の店が出しているため。実測（2026-09-28）で重複していた598枚の
  うち290枚は組の中の店が全部違い、足すと 598 → 328枚に減った。
  **同じ店で名前も同じものは、そのままにする**（分ける材料が無いのに番号を
  足しても読み手の役に立たない）。
- **手元の pytest とプレビューサーバを同時に動かさない。** `http.server` が
  `dist/` を掴んでいると、ビルドを伴うテストが止まる（2026-09-28 に実際に踏んだ）。
- **落とす順は「頭 → 途中 → もう一度頭」。** 名前の途中の宣伝を落とすと記号が
  先頭に来る（「TIMESALE！1,730円～ ハンディファン」→「！1,730円～ …」）。
  `strip_mid_promo` のあとに `LEAD_MARK`/`LEAD_PROMO` をもう一周かける。
  **飾りの記号には絵文字・矢印・音符も入れる**（✨⇒♪ で止まって、その後ろの
  宣伝の囲みまで残っていた。記号で始まる名前は実測87件→63件）。
  宣伝だけが入っていた囲みは殻（`≪≫`）が残るので `EMPTY_BRACKET` で落とす。
  残る63件は《ソフトタイプ対応!》〈メーカー保証1年付き〉のような**商品情報の
  囲み**なので、これは残すのが正しい。
- **検索はひらがなもカタカナに寄せる（`norm`）。** `NFKC` は半角カナを全角カナに
  直すが（ｲﾔﾎﾝ→イヤホン、実測476件に当たる）、ひらがなはカタカナにしない。
  「いやほん」「すいっち」「けーす」はどれも0件だった（カタカナなら476/655/1,423件）。
  日本語は仮名の並びが同じなので、U+3041〜U+3096 に +0x60 するだけで足りる
  （辞書は要らない）。索引側も同じ `norm` を通すので両側に効く。
- **見守りから消えた商品は、消えたと書く。** 登録した商品が記録から外れる
  （販売終了・取得対象から外れる）ことがあり、「0件」とだけ出していた。
  何件が記録から外れたのかを添える。
- **`og:image` に SVG を渡さない。** X も Facebook も LINE も og:image の SVG を
  描かないので、共有しても絵が出ていなかった。
  商品ページ（全体の99%）は**楽天の商品写真**を渡す（ページ内で既に出している
  同じ画像なので、新しく持つものは無い。`twitter:card` も
  `summary_large_image` にする）。トップと一覧は `icon.og_png()` が作る
  1200×630 の PNG。**文字は入れない**（標準ライブラリだけでは日本語の字が
  描けない。背景と印だけでも「絵が出ない」よりは伝わる）。
  `og.svg` は残す（数字入りで、ページに埋め込んで見せるぶんには軽い）。
- **バックスラッシュはヒアドキュメントでもコード生成でも潰れる。**
  `b"\x89PNG\r\n\x1a\n"` を書こうとして PNG の署名が改行に化け、
  同じ事故を2回踏んだ。`B = chr(92)` で組み立てるか、
  書いたあと必ず `ast.parse` で確かめる。
- **印刷の指定を置く（`@media print`）。** 価格の記録を紙やPDFに残したい人が
  要るのは商品名・価格・図・表だけ。上下の並び・切り替えボタン・ページ送り・
  次の行き先は消し、リンクの下線も外す。**出典（アフィリエイトの表示）は残す**
  （どこで見た価格か分からなくなる）。
- **一覧の題は中身に合わせる。** ジャンルのページは「◯◯の値下がり」という題で
  そのジャンルの**全商品**を出していた。実測（2026-09-28）でパソコン・周辺機器
  1,528件のうち値下がりは3件しか無い。中身を値下がりだけに絞ると13,000ページへの
  導線が消えて索引から落ちるので、**絞るのではなく題のほうを直す**
  （「◯◯の価格記録」＋「値下がりの大きい順に並べていますが、値下がりして
  いない商品も含みます」）。他の一覧（値下がり・最安値圏・値上がり・よく動く・
  期限が近い・最安値更新・ポイント込み）は題と中身が一致している。
  **日付別も同じ理由で「◯月◯日 の値下がり」から「◯月◯日 に安くなった商品」へ
  変えた**（実質価格が下がったものを含めたため）。今日ぶんは「今日の値下がり」と
  「ポイント込みで安くなった商品」の2枚に分かれているが、過ぎた日は1枚にまとめて
  いる。その旨を `/archive/` の前書きに書いてある。
- **3階層のページには3段のパンくずを置く（`breadcrumb2`）。** ジャンル
  （トップ → ジャンル別 → パソコン・周辺機器）と日付別（トップ → 日付別 →
  2026-09-26）に道しるべが無かった。一覧そのもの（最安値圏など）は2階層で、
  上の並びの `aria-current` で足りる。ページ送りの奥でもリンク先が
  `../../../` と合うことを確かめる。
