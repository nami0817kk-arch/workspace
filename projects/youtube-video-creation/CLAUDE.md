# 海外サッカーのニュース動画をつくる

台本(Markdown)から、動画・音声・BGM・字幕・サムネイル・概要欄までを書き出すパイプライン。
参考にしているチャンネル: https://youtube.com/@uwasathefootball2

## 動画の型は3つ。題材ごとに選ぶ（2026-09-08）

14チャンネルを同じ物差しで測ったら、ニュース番組の形はこちらだけで、
伸びている側は尺も形式もバラバラなのに**「誰かの声がある」点だけ全員同じ**だった
（[docs/news-sources.md](docs/news-sources.md)）。他所で回っている作りは
こちらでも作れるようにし、**どの型で作るかは題材ごとに決める**（ユーザー指示）。
取材メモの `format:` で切り替える。詳細は [docs/research.md](docs/research.md)。

| `format` | 中身 | 他人の声の下限 | まとめ | 手本 |
|---|---|---|---|---|
| `news`（既定） | キャスターと解説が事実を掘る。問い→節→答え。確度の札 | 40% | あり | ― |
| `voices` | 事実は最初の30秒。残りは反応を1件ずつ読む | 70% | 無し | 2chサッカーの噂話・サッカーラボ（他人の声83%） |
| `quote` | 選手・監督が自分で語った言葉を切り出す。30秒前後 | 60% | 無し | KOALA SOCCER（登録1,890で中央値21万回） |

- 型を提案するのは題材を出すとき。**「この題材は voices で」と一緒に出す**
- 反応の行は `voice: 現地サポ` `voice: ネット民` `voice: 海外のファン`。
  この3つは匿名の群衆として1件ごとに声が変わる（`voice_crowd`）。
  **反応は実在する投稿・記事からだけ引く。**節の `sources` にスレや記事のURLを置く
- 以下の決まりは **news の型**のもの。voices / quote は問いも答えも立てない

## news の型（変えないこと）

- **1本1テーマ。**話を詰め込まない。尺は**1〜3分半**
  - 目安は1〜2分（参考3チャンネルの実測は 1:01〜1:59。唯一の長尺は
    登録者が近いのに**再生が1桁少なかった**）
  - **ただし目安であって上限ではない**（2026-09-07 ユーザー「長くても良い」）。
    引用が主役の回は3分でも成立する。**短くするために発言を削るのは本末転倒。**
    `review` の上限は210秒
  - 同じ日に「尺は気にしなくてよい」とも言われている。秒単位で詰める話はしない
- **1日9本。**枠は13（日本人5・試合結果2・ロマーノ1・プレミア2・ラリーガ1・その他2）。
  同じ話題を2つの枠へ入れない
  - **日本人は「1日に5枠」という割り当ての制約。**全体の傾向を寄せるものではない。
    一度 `weights.japanese` を入れたところ朝の3枠が全部日本人選手になったので外した
    （2026-09-05 ユーザーの訂正）。**枠で担保して、点では寄せない**
  - 2026-09-07 に 3枠 → 5枠（ユーザー判断）。各チャンネルの**最高再生**を並べたら、
    サッカー知恵袋の人気上位15本のうち**11本（73%）が日本人・日本代表**だった
  - **試合結果の枠2つ**も同じ日に新設した。2chサッカーの噂話は直近1日で、
    結果の動画が13万回×2、順位表が6.7万回。移籍の噂と同じかそれ以上に見られている。
    `results --write` で候補にして、`require_kind: match` の枠で拾う。
    試合が無い日は**空く**（移籍の話では埋めない）
  - 候補の選び方は**2系統**。1つめは新しさ・媒体数＝**速報としてどれだけ大きいか**。
    2つめは集約サイトの Points＝**いま実際に読まれているか**。
    `popular_1` は2つめだけで決める。**日本人には絞らない**
  - `popular_1` は枠の先頭に置く。後ろだと人気の候補を他の枠が先に取ってしまう
  - 2026-09-04 に 5本（日本人1本）から変更。さっかー情報館は直近30本の
    ほぼ全部が日本人選手で、登録1.73万に対し54万回の動画がある
  - **枠は埋めるためのものではない。**`min_score`（既定5点）に届かない日は
    空ける。実測で、9本に増やしたとたん2点のブログ雑感が枠に入った
  - 該当する候補が無い日も、別の話で埋めず**空ける**
- **構成は「タイトル → 事実 → 反応」の往復**（2026-09-07）。伸びている3チャンネルの
  直近4本を文字起こしで測って合わせた（[docs/video-quality.md](docs/video-quality.md)）
  - **1行目はタイトルをそのまま読む。**4本とも最初の2〜5秒でタイトルを読み上げていた。
    クリックした人が「これで合っている」と確かめられる。問いは読まず、画面に出す
  - **他人の声が尺の4割以上。**反応の節は**最後**に置き、最後の1件で終わる
    （2026-09-08 ユーザー「他人の声のところは他のチャンネルを参考に」。
    サッカーラボ 25.5万回の文字起こしは、事実30秒のあと反応を1件ずつ読んで切れていた）。
    反応の後ろに語りの節があると `draft` が止める。見通しは反応の前に置く。
    画面では匿名の反応が上に積み上がる（renderer の stack）。1件は30字目安・45字まで
  - **画面はその人の写真が主役**（2026-09-08 ユーザー「全体的に動画のクオリティを上げたい」）。
    冒頭の節はサムネの写真を敷き、写真のある行は右半分いっぱいに写真、左は同じ写真を
    ぼかした敷き布。参考は人物の実写が画面いっぱいで、こちらは枠付きの小さなカードだった
  - **公開と同時に最初のコメントを書く**（2026-09-08 ユーザー指示。Gemini の答え1）。
    問い＋「納得なら高評価、違うならコメントで」の誘い。動画の中では登録を頼まない。
    `comment <出力先> <videoId>` で書く。**固定は API にできない**ので Studio で行う。
    文面は `src/comments.py` が作り、結びは動画ごとに変わる
  - **冒頭の1行目にサムネと同じ伏せ字の一言**（左上・`thumbnail_points`）。Gemini 2026-09-08 の
    答え3。タイトルで伏せた答えを、最初の3秒の絵にも同期させる。クリックした人が同じ
    言葉を見て「合っている」と確かめられる
  - **冒頭の1行目に登録カード**（左上・チャンネル名＋赤い「チャンネル登録」）。参考は
    0.5〜2.5秒にこれを出し、読み上げでは頼まない。`video.channel_name` で出す
  - **まとめの節は無い**（2026-09-08 ユーザー「まとめはいらない」）。
    それまでは答えの1行だけ残していたが、それも読まない。答えは節の中で言う。
    `answer` は書かなくてよい
  - **締めの挨拶を読み上げない。**「続報はチャンネル登録して…」は毎回同じで8秒使う。
    最後のカードと概要欄に置けば足りる
  - **話速は変えない。**参考5.8字/秒・こちら5.3字/秒でほぼ同じだった（測って分かった）
- **ニュースを読む人と、誰かの声を代弁する人**（2026-09-05 にユーザーが決定）。
  - `キャスター:` … 事実を伝える。声は固定
  - `<人の名前>:` … **その人の声を代弁する。**話者名にその人の名前を書く
    （`キャラガー:` `イラオラ監督:` `ネット民:`）
  - **匿名の反応は行ごとに声が変わる**（2026-09-07）。`voicevox.voice_crowd` に
    書いた名前（いまは `ネット民`）は、**発言の文字から声を選ぶ**。20件つづけて
    同じ声だと一人の独白に聞こえる。同じ発言はいつも同じ声で、作り直しても変わらない
    - **決め打ちされた声は群衆に使わない。**名前のある人と同じ声で匿名の書き込みが
      読まれると、その人が言ったように聞こえる
  - **代弁の声は人ごとに変わる。**`voicevox.voice_pool` から名前で選ぶので、
    config に書かなくても声が付き、**同じ人はいつも同じ声**になる
    （動画をまたいでも変わらない。乱数だと「前回と声が違う」が起きる）
  - **男の人には男性の声**（2026-09-07 ユーザーの指示）。話者はほぼ全員が男性
    （選手・監督・解説者）なので、**既定は男性のプール**。女性と分かっている人だけ
    `voicevox.voice_female` に名前を書くと、女性のプールから選ぶ
    - 男女は**実測で分けた**。VOICEVOX の全40キャラを1文ずつ喋らせて基本周波数を
      測ったら、男性110〜175Hz・女性205Hz以上できれいに分かれた
    - **男性の声は8つしかない**（99離途 / 52雀松朱司 / 11玄野武宏 / 21剣崎雌雄 /
      53麒ヶ島宗麟 / 51紅桜 / 67栗田まろん / 100黒沢冴白）。13番（青山龍星）は
      男性だが「解説」が使っているのでプールに入れない
    - 8つしかないので**同じ動画に9人以上出せば必ず衝突する。**よく出る名前は
      `voice_fixed` で先に決めてある。衝突は `review` の「声の重なり」が止める
  - **42番（ちび式じい）は使わない**（2026-09-07 ユーザーの指示）。老人の声で、
    メッシとモウリーニョがこれで喋っていた。`voice_banned` に書いてあり、
    **プールに入れ直すと config の読み込みで止まる**
  - **名前ごとに声を決め打ちできる**（2026-09-07 ユーザーの指示）。
    `voicevox.voice_fixed` に `名前: style_id` を書くと、ハッシュを使わずその声になる。
    **ハッシュはまれに衝突する。**実際にメッシとモウリーニョがどちらも style 42 で、
    同じ声で喋っていた。いまは メッシ=20 / モウリーニョ=11
  - **別人が同じ声になっていないか、機械で見る。**`draft` の検証と
    `review` の「声の重なり」が突き合わせる（縦型にも当てる）
  - 候補は話者ごとに「ノーマル」を1つずつ。同じ人の別スタイル（あまあま等）を
    混ぜると聞き分けられず、**別人だと分からない**
  - 2026-09-04 にキャスターと解説の2人へ、2026-09-05 にこの形へ変えた。
    **元の設計（報道番組の単独ナレーション）とは正面から衝突する。**
    見ていて飽きないことを、事実を伝える部分の硬さより優先した判断
- **画面に立ち絵は出さない。** 掛け合いは声と話者バッジで表す
  - 一度 `show_characters: true` にして立ち絵を出したが、**仮素材が巨大で
    移籍カードに左右から重なり、選手名が読めなくなった**（実測）。
    `generate_character` はコード内に「ゆっくり風の丸顔立ち絵（仮）」と
    書かれている仮素材で、報道内容と釣り合わない。
    立ち絵に足る素材を用意できたら、改めて検討してよい
- **反応は画面に積む**（2026-09-07）。匿名の反応が続くあいだ、**前の3件を見出しの
  上に白い吹き出しで残す**。参考チャンネルは4〜5件を残していて、途中から見た人も
  文脈を拾える。こちらは1行ずつ消えていた。語り（キャスター）が入ったら積み直す
  - 古いものほど薄くする。いちばん下（新しい）がはっきり見える
  - **Xの投稿は「有名人」だけ画像で使える**（2026-09-08 ユーザーが許可）。
    それまでは一切使わない方針だった（2026-09-02）。**2つあった理由のうち、
    片方だけが解けている**ことを忘れない
    1. **他人の著作物である。**静止画は Content ID の対象外なので自動検出は
       されないが、削除要請が来れば警告が付き、**3回でアカウントごと止まる**。
       → この危険は**ユーザーが引き受けると決めた**。引用の体裁（出典を明示し、
         必要な長さに留め、本編の主役にしない）は守る
    2. **@ハンドルが画面に写る。**匿名の一般人は「@ハンドルを出さない」決まりで、
       **これは解けていない**。→ だから誰の投稿でもよいわけではない
  - **誰が「有名人」かは `accounts:` の一覧で決める。**記者・クラブ公式・選手など、
    公の場で発言している人。載っていなければ `xshot` が止める（人が足す）

    ```bash
    python -m src.cli xshot https://x.com/FabrizioRomano/status/… assets/posts/romano
    ```

    - 取った画像は台本の `image:` に。**投稿URLを `sources:` に入れる**
      （`review` の「投稿の出典」が突き合わせる。引用は出どころを示すのが条件）
    - **サムネイルには使えない**（切って文字を重ねるため、改変不可の印を付けてある）
    - 投稿に**報道写真が貼られていることがある**。その写真も他人のもので、
      危険が重なる。**選ぶときに見る**
    - `xshot` は手元の Chrome（リモートデバッグ）にぶら下がる。
      `pip install playwright` が要る（ブラウザ本体は落とさない）
  - 匿名の反応は**文字だけ**を積む。スクリーンショットは使わない
- **クラブのエンブレムを小さく添える**（2026-09-08 ユーザー判断）。
  **CCの表示は当てにならない。**Openclipart や VectorPortal に上がっている
  エンブレムは、なぞって上げた人が CC0 を付けているだけで、
  **その人にクラブの商標を解放する権利は無い**（実際に上げた人と説明を確認した）。
  Google 画像検索の「クリエイティブ・コモンズ」絞り込みも、
  **サイトの主張を見ているだけで元の権利までは見ていない。**
  - つまりこれは**引き受ける危険**であって、権利が晴れているわけではない。
    Xの画像と同じ扱い（削除要請が来れば警告、3回でチャンネルが止まる）
  - **小さく添えるだけ。**クラブ名の札の横など。**サムネの主役にしない**
  - クラブが認めている・提携しているように見せない
- **出典は概要欄に書く。画面には出さない**
- **背景は実写の動画**（2026-09-07 に静止イラストから変更）。
  自作の静止画だと**30〜50秒のあいだ画面がほとんど動かない。**
  ショートの競合は実際の試合映像で、権利の関係でそれは使えないが、
  **「動いていない」ことは埋められる。**素材は `stock` で取る
  - 節の性格で割り当てる（`research.BACKGROUND_BY_SECTION`）。
    発表＝スタジアム / 試合＝ボール / 反応＝観客 / 見通し＝練習 /
    **数字と整理だけは模様の無い下地**（読みやすさを優先）
  - **素材が無ければ静止画に落ちる。**取っていない環境でも壊れない
- **カードは勘で決めない**（2026-09-07）。それまで回によって4〜7枚とばらつき、
  「なぜここに表を出すのか」を言葉にできなかった。**文の役割で決める**
  （`src/cardrule.py`）

  | 文が言っていること | カード |
  |---|---|
  | 代弁の行／鉤括弧 | **引用** |
  | 時系列＋数字2つ以上 | **表** |
  | 数字が3つ以上 | **棒グラフ** |
  | 列挙 | **箇条書き** |
  | それ以外 | 出さない |

  - `review` が突き合わせて知らせる。**止めはしない**（基準は出発点で、
    別の型を選ぶ場面はある）。ただし**気づかずに落ちる**ことは防ぐ
  - 見た目が変わらない時間は、本編の20秒とは別に**8秒**で見る
  - BGM は台本の【】から選ぶ。**悲報と速報を同じ曲にしない**
    （速報=breaking / 悲報=somber / 朗報=victory / 詳報=calm）
- **サムネイルには人の顔を必ず入れる**（2026-09-05 ユーザーの指示）。
  参考3チャンネルはどれも顔が全面。台本に `thumbnail_photo:` と書く。
  **`review` が必須項目として止める**（人の注意に頼ると忘れる。実際に忘れた）
  - **蛍光イエローの帯1枚に、黒の1行目と赤の2行目**（2026-09-07 に `news` から変更）。
    最高再生の2本（64万回・25万回）を実際に見て合わせた。帯の上には
    **書き込みの断片**を白い小窓で出す（`thumbnail_reaction:`。無ければ台本から拾う）
    - 向こうの下地は**試合のワンシーン**。**放送映像は使わない**決まり（2026-09-05）は
      変えないが、代わりが2つある（2026-09-07 ユーザー判断）
      1. **数字の図**（`statboard`）。参考の最高再生64万回の中身は、試合映像ではなく
         **走行距離のスタッツ画面**だった。数字の図なら自分で作れて権利の問題が無く、
         一覧では「試合の画面」に見える。`review` の「サムネの顔」はこの図を顔の代わりに認める

         ```
         python -m src.cli statboard assets/stats/run.png --title 走行距離 --unit km              --row ヴィルツ=12.3 --row ソボスライ=11.6
         ```
      2. **Commons の試合写真**（`matchphoto`）。実際の試合の写真が CC BY / CC BY-SA で
         ある。**人物は特定していない**ので、台本でも「その試合の写真」とは書かない。
         建物・記章・ロッカールームは機械で落とす（実測で1件目に出た）
  - **縦長の写真は右に置き、文字を左に寄せる**（自動で切り替わる）。
    写真は**枠を埋めるまで拡大する**（画面の58%）。高さだけ合わせていた頃は、
    細い縦写真だと幅が足りず、**左半分がぼかしだけ**になっていた
    （2026-09-08 ユーザー「ただのぼかし」）
  - **顔は並べられる**（`thumbnail.photos` に2〜3枚）。縦長を1枚だけ右に
    置くと左がぼかしで埋まるが、**並べれば全面が写真になる。**
    参考チャンネルの実物も全面が写真で、顔を3枚並べた回があった。
    話に噛み合う組み合わせにする（デンベレの回なら、挙げられなかったヤマルと並べる）
  - **左の余白には言葉を積む**（`thumbnail.points`、3つまで。写真が1枚のとき）。
    **ただし答えは置かない**（2026-09-08 ユーザー指摘）。最初は
    「挙げられた3人の名前」をそのまま並べたが、**タイトルで答えを隠している
    意味が消える。**参考チャンネル（2chサッカーの噂話・10.3万）の実物を見ると、
    答えの位置は **●● で伏せてある**

    | 向こうの実例 | 再生 |
    |---|---|
    | ソボスライ「唯一やりたくないポジションは**●●です**」 | — |
    | ロドリ、プレミアとの差に困惑「弱い…**弱すぎるだろ**」 | 13万 |
    | レアルソシエダさん、久保をベンチにした**結果** | **21万** |

    置くのは**引きになる断片**（「1人目 ●●●●」「本人が望むのは ●●」）。
    `draft` が、答えの文字列がそのまま入っていないか見る
  - 全面に敷くと
    16:9 に切った時点で顔が残らず、見出しとぶつかる。切る位置を変えても解けない
  - 横長は全面。顔の位置が合わないときだけ `thumbnail_focus:`（0.0=上端/1.0=下端）
  - 写真は `python -m src.cli portrait <置き先> <名前…>` で取る。
    **被写体を Wikidata で確かめ、ライセンスも判定してから**落とす。
    名前は**日本語と英語の両方**を渡す（被写体の記載がどちらかに寄っている）
  - **ライセンスは用途で変わる**（2026-09-06 ユーザーの判断）。`portrait` が機械的に見る

    | | サムネ・背景（切る/ズーム） | 本文の `image:`（そのまま出す） |
    |---|---|---|
    | CC0 / PD / CC BY / **CC BY-SA** | ○ | ○ |
    | **CC BY-ND** | × | **○**（`--whole` で取る） |
    | CC BY-NC 系 | × | × |

    - **BY-SA を許可した。**日本人選手は CC BY だと引き写真しか無く、
      「顔は必須」と両立しなかった。継承条件（同じ条件で公開）を受け入れる側を選んだ
    - **ND は「改変しなければ使える」。**CC 4.0 は媒体・形式のための技術的変更は
      改変物を生まないと明記していて、**本文の写真は縮小しているだけ**
      （`_picture` は min で縮める。切り取りもズームもしない）。
      サムネは16:9に切って文字を重ねるので不可。**`review` が印を見て止める**
    - NC は収益化と両立しないので、どこでも使わない
  - **機械が通しても、必ず目で見る。**被写体もライセンスも通ったのに使えない
    写真を、2026-09-06 に4回つかんだ:
    - 販促用の合成カード（ロゴと惹句が入っている）
    - 背番号側からの引き写真（顔が写っていない）
    - 全身の動作写真（顔が豆粒。元画像も小さく拡大できない）
    - **前所属クラブのユニフォーム**（別クラブの話に見える）
    最後の2つは `--crop x,y,w,h` で顔だけ切り出せば直る（CC BY は改変可）。
    どれを使うかは `--file` で指定する
  - 日本人選手は CC BY だと引き写真ばかりだった（中村敬斗・鎌田大地は顔が無い）。
    **BY-SA を開けたのはこれが理由。**それでも見つからない日は、
    記事に出てくる別の人（監督・共演者）の顔を使う
  - **どうしても顔が取れない題材は、作らない**（2026-09-07 ユーザーの判断）。
    実例: U-19日本代表の予選突破。徳田誉・浅田大翔・村松秀司は Commons に
    写真が無く、山口智監督は現役時代の全身写真しかなかった。
    **若手・アマチュア・育成年代は、この形になりやすい。**
    サムネを作れないまま無理に出すより、その日は別の題材にする
- **ショート中心にはしない**（2026-09-07 ユーザー判断）。実測ではショート14本で
  3,079再生・本編24本で136再生と桁が2つ違うが、**本編を続ける**。
  1本6再生は「負けた」ではなく「まだ露出が無い」値で、参考3チャンネルは
  ショートを1本も出さずに本編で5〜18万回出している。**この話は蒸し返さない**
- **Jリーグは扱わない**（2026-09-07 ユーザー判断）。国内リーグは競合が薄く、
  トリベラフットボールは登録8,130人で10万回を出しているが、
  チャンネル名「海外サッカーの理由」と衝突する。**この話は蒸し返さない**
- **定型シリーズを回す**（2026-09-07）。分野を横断して24本を並べたら、
  **どのチャンネルも節ごとに順位表を出していて、毎回伸びていた**
  （トリベラ10万・6.1万、噂話6.7万）。中身は数字だけで取材も写真も要らない。
  **繰り返し見にくる型**をこちらも持つ

  ```bash
  python -m src.cli standings england --out assets/stats/pl.png
  ```

  - 取材計画は `table` ルーチン。順位を読み上げるだけにせず、**表から1つ話を拾う**
  - 画像はサムネの下地に使える（`review` は数字の図を顔の代わりに認める）
- **タイトルの頭に人名かクラブ名を置く**（2026-09-07）。参考24本の**54%**が
  名前から始まっていた。こちらの直近7本は**86%が【札】から**始まり、名前が後ろだった。
  検索にも推薦にも最初の数文字が効く。`review` の「タイトルの主語」が見る
- **札は12種類**（速報・朗報・悲報・詳報・衝撃・緊急・独占・現地反応・神試合・
  異変・決着・波紋）。4つ固定だと毎回同じ顔になる。向こうは動画ごとに強い言葉を
  作っていた。**増やしても中身と食い違わせない。**札を足したら
  `audio_gen.PREFIX_MOOD` にも足す（抜けると悲報と朗報が同じ曲で鳴る）
- **タイトルを定型にしない**（2026-09-08 ユーザー指摘）。
  「答えを隠す」を守ろうとした結果、**9本中7本が「〜がこちらです」**で終わっていた。
  隠し方は毎回考える。**問いかけ・引用で切る・体言止め**など形はいくつもある。
  - 原因は点検の側にあった。`TITLE_HOOKS` に決まった語尾しか入れておらず、
    疑問符の無い問いかけ（「〜のか」「〜たか」）を弾いていた。
    **検査が定型化を招いていた。**問いの形と引用終わりを認めるようにした
  - 揃っていないかは `variety` の「結び方」が見る（末尾6字が半分を超えたら知らせる）。
    **1本ずつの点検では「毎回同じ」は見えない**
- **タイトルは答えを言い切らない**（2026-09-07）。各チャンネルの**最高再生**を
  並べたら、上位はほぼ全部が答えを隠していた（[docs/video-quality.md](docs/video-quality.md)）
  - 「解説南さん『鈴木彩艶に関しては・・・』」25万 /「新監督を迎えたリヴァプール、朗報」35万
  - 「〜がこちらです」「〜が話題に」「〜してしまう」「〜に異変」
  - こちらの直近14本は**全部が言い切り**で、タイトルで用が足りていた
  - **隠すことと嘘をつくことは別。**中身では必ず答える（まとめの答え1行は残してある）
  - `draft` が助言し、`review` の「タイトルの型」が止める

## 事実の扱い（いちばん大事なところ）

**検索エンジンのAI要約は使わない。** 実測で8回、実在しない移籍を作文してきた。
使ってよいのは、記事の見出しそのものと、投稿の本文そのものだけ。

- 見出しに書いていないこと（得点時間、xG、契約年数）は**使わない**
- `…` で切れている引用を、**推測で補わない**。切れたまま引くか、使わないか
- クラブが発表していないものを「確定」と書かない

確度は4段階。画面と `tier` を必ず一致させる。

| | 使ってよい根拠 |
|---|---|
| **確定** | クラブ・リーグの公式発表まで辿れたもの。および `config/sources.yaml` の `accounts` で `tier: 確定` にしたアカウントの投稿（2026-09-07 現在ロマーノのみ） |
| **報道** | 報道機関の記事。**1社でよい**（2026-09-07 のユーザー判断。それまでは2社以上の一致を条件にしていた） |
| **未確認** | SNS段階、噂まとめ。単独では根拠にしない |
| **背景** | 経緯の説明。事実の主張ではない |

上限は出典の群で決まる（`domain_tiers`）。タブロイド・まとめは `rumour` 群なので、
それ単独では未確認までしか置けない。`dailymail.com` と `nofootynolife.net` は
2026-09-07 に `rumour` へ登録した（それまでは網に無く、上限を決められなかった）。

`config/sources.yaml` の `domain_tiers` が、情報源の群ごとに置ける上限を決めている。
`draft` と `lint` がこれと突き合わせて、上限を超えた確度を止める。

### まとめサイトの扱い

情報源にまとめサイト（footballnet / サカサカ10）を入れてある。**匿名掲示板の
書き込みを集めたもの**なので、確度は `rumour` 群＝**未確認どまり**。
見出しが「【速報】」「Official」でも、そこだけを根拠に上の確度へは上げられない
（`draft` と `lint` が機械的に止める）。

使ってよいのは次の2つだけ。

- **いま何が話題になっているか**を掴む手がかり（題材選び）
- そこで**引用元として示されている報道機関の記事**。その場合は元記事を直接当たり、
  出典もそちらを書く

書き込みそのものを引くときは、上の「世の中の声」の決まりがそのまま適用される。

### 「世の中の声」を入れるとき

- 識者・関係者の発言は、**名前と媒体を特定できるものだけ**（確定または報道）
- 匿名のファンの声は **未確認** 扱い。@ハンドルは画面に出さない
- **「多い」と言うには数える（2026-09-04 に方針変更）。**
  `python -m src.cli reactions <まとめのURL>` が書き込みを取り出して数える。
  台本には「47件中12件」のように**件数と母数**を書く。数えていないなら言わない。
  - 元の決まりは「数を数えた言い方をしない。数えていないので」だった。
    **数えられるようになったので、前提が変わった。**
  - まとめサイト自身の要約は使わない。実測（2026-09-04）で、
    「反応は総じて冷ややか」と書いてあるスレを数えたら 47件中4件（9%）だった。
    **要約は誇張されている。**数えた自分の結果だけを使う
- **読み上げる反応は10〜20件。1件は30字まで**（2026-09-07 にユーザーが決定）。
  元の決まりは「引用は数件まで」だった。伸びている3チャンネルの直近4本を
  文字起こしで測ったら、**他人の声が尺の58%・19.2件・1件3.1秒**で、こちらは
  **14%・2.2件・1件39字**だった。ここが再生数の差の中身なので、件数の側を変えた
  - **短く刻む。**1件が長いと、画面も声も止まる。20字を超えるものは切らずに落とす
    （2026-09-07 に30字から締めた。実測は1件3.1秒＝約16字で、30字は5.5秒ぶん）
    （途中で切ると意味が変わる。「…」を推測で補わない決まりと同じ理由）
  - `python -m src.cli reactions <スレURL> --say` が、取材メモに貼れる形で出す
  - **母数は必ず出す**（「47件中12件」）。レス番号とURLも従来どおり全件残す
  - スレ全体を写すのは引用ではない。**選ぶ**。まとめサイト自身の要約は使わない
  - `review` の「他人の声の量」「反応の刻み」が、書き出したあとに機械で見る
- 出典の無い反応カードは `draft` が弾く

## 毎日の流れ

**台本にユーザーのOKが出てから書き出す**（2026-09-08 の指示）。
`draft` で台本ができたら、**そこで止めてユーザーに見せる。**
`build` / `short` は、OKが出てから走らせる。

見せ方は、台本をまとめた1枚のページ（Artifact）にしてリンクを渡す。
スマホから読める形にする。**台本が増えたら同じページを更新する**（URLは変えない）。
出すのは、読み上げる文・話す人・確度・出典・尺・他人の声の件数。

**理由:** 直すなら書き出し前がいちばん安い。書き出したあとに直すと、
音声の合成からやり直しになる。実際 2026-09-08 に、見せる前に書き出しを
始めてしまい、途中で止めた。


```bash
python -m src.cli today      # いつでもこれ。次に打つコマンドを1つだけ返す
```

```
gather ─→ lint ─→ saga ─→ pick ─→ plan --write ─→ draft ─→ build ─→ review ─→ upload
 収集      検証     続報     選定      取材メモ       台本      書出      点検      公開
                                    ↑ --reactions <まとめURL> で反応12件が入る
```

試合結果は `results` で別に取る。フィードは移籍ニュース中心で、試合結果は
数時間で流れ切る（実測で1日177件拾って試合結果は0件だった）。

```bash
python -m src.cli results --write        # 昨日の試合を候補にする
python -m src.cli results --date 2026-08-30 --league germany
```

`--write` を付けると、試合ごとの採点・得点者・**国籍**まで見て
`goals` / `numbers` のフラグを自動で立てる。手で立てる前提の欄は、
実測で365件中0件しか立たなかったため。
**`reaction`（賛否が割れているか）は機械で立てない。** 数えていないので。

- **`plan --routine <枠> --write --reactions <まとめのURL>`** … 取材メモの雛形に
  **反応を12件入れた状態**で作る（2026-09-07）。点検は「他人の声が尺の4割以上」を
  求めているのに、雛形には空の `say` が1つしかなく、手で10件書くことになっていた。
  母数・レス番号・出典もそろって入る。URL を渡さなければ今までどおり空
- `gather` … フィードと貼り付けをまとめて候補ファイルに（`--paste` で検索結果を混ぜる）
- `doctor` … 仕組みが効いているかの健康診断。週に1回は見る
- `standings <リーグ>` … **順位表**を取る（定型シリーズ）。`--out` で画像も書き出す。
  england / spain / germany / italy / france / netherlands
- `stock <探す言葉>` … **内容に合う実写の背景**を Pexels / Pixabay から取る。
  背景は決め打ちにしない（2026-09-05 のユーザー判断）。自前で描いた PNG に
  模様を足すより実写のほうが強い。取ったものは credits.json に控え、
  概要欄に撮影者が出る。鍵は `platform/ai-lab/.env`（worktree には来ないので
  環境変数で渡す）
- **投稿は時間で散らす**（2026-09-07 の実測）。参考にしている 2chサッカーの噂話は
  直近24時間で 8/18/20/21/22/23 時間前と**1時間に1本ずつ**出していた。こちらは
  13時間前に4本と固めていた。まとめて出すと自分の動画同士で枠を奪い合う。
  `upload` が前の投稿から45分たっていなければ知らせる（止めはしない）
- `upload --dry-run` … 送る前に中身を確認。**投稿は取り返しがつかない**
- **サムネイルの制限は、動画の枠とは別物**（2026-09-06 実測）。
  6本続けて上げたら**動画は全部通り、サムネイルだけ6本とも429**になった
  （`uploadRateLimitExceeded`）。10分おきに試して30分で全部付いた。
  - **投稿からやり直さない。**同じ動画が二重に上がる。
    `setthumb <出力先> <動画ID>` でサムネイルだけ設定する
  - **本編とショートの両方を出す**（2026-09-07 ユーザー決定）。
    再生数はショートに偏っている（14本で3,079、本編24本で136）が、
    **本編が弱いのではなく、登録者がいないので配られていない。**
    ショートに寄せる案は出したうえで、両方続けると決めた。**蒸し返さない。**
    1題材につき本編1本＋ショート1本＝**投稿枠を2つ使う**ので、
    上限との兼ね合いで題材の数が決まる。
  - **投稿の本数上限は、コンソールのどの数字とも一致しない。**
    2026-09-07、「Video Uploads per day」が 49/100、Queries が 8,138/10,000 と
    どちらも余っている状態で `uploadLimitExceeded` に弾かれた。
    弾いているのは**チャンネル側のスパム対策の上限**で、
    **残量を知るAPIも画面も存在しない**（上限も残数も非公開）。
  - **手作業（Studio の画面）でも弾かれる。**2026-09-07 に実際に試して確認。
    チャンネル単位の上限なので、**経路を変えても回避できない。**
    「APIが駄目でも手で上げれば」は通らない。
  - **解除は「エラーが返った時刻から24時間」。**固定時刻でも、
    1本ずつ空く方式でもない。10:36 に弾かれ、12:41 も 16:02 も弾かれた。
    転がる窓だと考えて2回外した。
  - **弾かれている間は投げない。**再試行を繰り返すと内部のタイマーが
    延ばされるとの報告がある。**測るつもりが解除を遅らせる。**
  - **「1日10〜15本」は上級機能が通る前の数字。**2026-09-07 の実測で、
    そのときは34本で引っかかった。**2026-09-08 に上級機能が承認されたので、
    いまの上限は分からない**（そもそも非公開）。
    **古い数字を今日の上限として使わない。**投げてみて、弾かれたら止める。
    数えるのは本編とショートの合計。
  - **上級機能を通すと上限が広がる。**2026-09-08 に承認され、
    前日の解除待ち（17:46）を待たずに投稿できた。**承認が解除を上書きする。**
    申請は YouTube Studio の設定→チャンネル→機能の利用資格（**PC版のみ**）。
    ビデオ通話なら1日以内に返事が来る。
    **確認に使った動画を消すと上級機能が外れる**ので触らない。
  - **上級機能が広げるのは「本数」の上限だけ。APIの枠は別**（2026-09-09 に確認）。
    2つは名前が似ていて混ざりやすいが、**返るエラーが違う。**

    | | 何が止めるか | エラー | 上級機能で変わるか |
    |---|---|---|---|
    | 本数 | チャンネル側のスパム対策 | `uploadLimitExceeded` | **変わる**（09-07 は34本で停止→09-08 に解消） |
    | APIの枠 | Google Cloud プロジェクトの割り当て | `quotaExceeded` | **変わらない** |

    こちらの控えで確かめた。**上級機能が承認される前の 09-05 に、すでに
    12,800 ユニット（8本）、09-06 に 54,400（34本）使えている。**
    既定の10,000なら6本で止まるので、**枠は最初から引き上げ済み**だった。
    枠を増やすのは Studio ではなく
    「YouTube API Services - Audit and Quota Extension Form」（Gemini にも確認）。
  - **上級機能が通ったことで、詰まる場所が入れ替わった。**
    以前は本数（34本）で止まっていたが、いまは**APIの枠**が先に尽きる。
    2026-09-09 に64本上げた時点で `quotaExceeded`。
    枠の実測はおよそ106,000〜110,000なので、**1日65本前後＝32題材**が上限。
    詳しくは `docs/handoff.md`
  - **二重投稿は `research/posted.json` の控えが止める**（src/posted.py）。
    同じ出力先を二度 `upload` すると、投稿せずに既存のURLを出して終わる。
    上げ直すときだけ `--again`。控えは投稿本数の残りも数えていて、
    残り3本を切ると「次に空くのは何時か」を出す。
  - **投稿処理を二重に走らせない。**2026-09-07 に、先の実行が本編8本を
    上げ終わる前に「サムネを付ける」つもりで2本目を起こし、
    japan/kubo/spurs/inter を二重投稿した上に、本数上限を使い切った。
    **起こす前に、走っている処理の出力を最後まで読む。**
  - **動画IDはハイフンで始まることがある**（例: `-gZ3P1gw8QU`）。
    そのままだとコマンドがオプションと解釈して失敗する。**`--` を挟む**:
    `setthumb -- <出力先> -gZ3P1gw8QU`。
    2026-09-07 に、これを制限（429）だと1時間半誤認した。
    **失敗の中身を読まずに再試行を重ねると、原因が見えない**
  - まとめて上げる日は、**サムネイルの設定に時間がかかる**前提で組む
- `redescribe <台本> <動画ID>` … 公開済みの概要欄に**写真のクレジットだけ足す**。

## ショート動画（2026-09-06）

**ショートの一覧はサムネイルを見ていない**（2026-09-09 に判明）。

`https://i.ytimg.com/vi/<id>/oar2.jpg`（1080x1920）だった。
これは**YouTube が動画から自動で作る縦の1コマ**で、
`thumbnails.set` で入れた画像（`maxresdefault.jpg`）ではない。

- **一覧の見え方を変えるには、動画の冒頭そのものを作り込むしかない。**

- そのため `_photo_stage` を**縦型でも効かせる**ようにした（それまでは
  `is_portrait` を素通しし、冒頭は枠付きの小さな写真カードだった）。
  いまは写真が 1080x1920 いっぱいに敷かれ、下だけ暗く落として見出しを乗せる
- **確かめ方の注意。**`i.ytimg.com` の高解像度URL（`qhd`）は生成前だと
  **404 を返し、その本文をそのまま画像として読むと灰色のプレースホルダに見える。**
  2026-09-09 に「まだ処理中」と3回誤認した。**HTTPの返りを見る**


```bash
python -m src.cli short <台本>                    # いちばん強い場面を自動で選ぶ
python -m src.cli quota                          # 枠の残り
python -m src.cli short <台本> --section 何が起きたか   # 節を指定する
```

本編から**冒頭＋1節**を切り出して 1080×1920 にする。60秒以内。

- **見積りは実尺より1割以上短く出る**（実測 2026-09-07: 見積り56秒 → 実尺66秒）。
  章の切り替えや間の処理が乗るため。**上限まで詰めると必ず超える**ので、

- **いちばん強い場面を使う**（ユーザーの指示）。11本を振り返ると、
  残ったのは全部「誰かの言葉」だった。点の付け方は

  - **まとめの節は選ばない。**答えを先に言うと、本編を見る理由が消える
  - カードも代弁も無い台本は、どの節も2〜4点で並ぶ。

  平均12秒目、映っているのは全体の2割だった。**ショートは数秒で見るか

## 質を保つ仕組み（2026-09-04）

**2026-09-08 に、読み上げの入っていない動画を25本公開した。**
VOICEVOX を起動していなかったため `backend: auto` が無音に落ち、
**長さだけ正しい無音のwav**が並んだまま書き出せていた。
音の大きさの点検は**BGMを見て -15dB で合格**するので、何も鳴らなかった。
**気づいたのはユーザーが耳で聞いたときで、機械は一度も知らせていない。**

- `create_backend` は**黙って無音に落ちない**。繋がらなければ止まる。
  無音でよいのは `--no-tts` か `backend: silent` と言われたときだけ
- `review` の「読み上げ」が、**BGM込みの動画ではなく音声ファイルそのもの**を見る
- **合格の条件が、確かめたい当のものを見ているか。**BGMが乗るだけで
  通る音量の点検は、無音を見つけられない


**書式の点検が緑でも、成果物を見るまで終わりではない。**この日に見つけた不具合は
7件すべて、目視か実測で出た。書式の点検は1件も拾えていなかった。

```bash
python -m src.cli review <台本>     # 完成品まで点検する（× があれば直す）
python -m src.cli contact <台本>    # 画面が変わるたびの1枚を並べた紙を作る
```

`review` は台本だけでなく **書き出した動画・字幕・概要欄** を見る。

| 見るもの | 落とすもの |
|---|---|
| 字幕の量 | 1枚38字を超える（テレビは全角15字×2行） |
| 字幕の中身 | 画面用の確度バッジが混ざっている（読み上げと食い違う） |
| 画面の切り替わり | 1画面が12秒を超えて止まる |
| **見た目の変化** | カードもテロップも変わらないまま20秒を超える |
| **サムネの顔** | `thumbnail_photo` が無い／写真が実在しない |
| 写真のクレジット | 使った写真の数だけ概要欄に出ていない（**CC BY は表示が必須**） |
| 読み上げの文 | 句読点が二重（合成音声が不自然に間を空ける） |
| 音の大きさ | -14 LUFS から2dB以上ずれる（YouTube の基準） |
| **読み上げ** | **合成した音声が無音**（BGMだけの動画になる） |
| **他人の声の量** | 尺の4割に満たない（参考3チャンネルは58%・19件） |
| **反応の刻み** | 1件が20字を超える（参考は1件3.1秒＝16字前後） |
| **1行目** | タイトルを読んでいない |
| **タイトルの主語** | 頭14字に人名もクラブ名もない |
| **まとめの長さ** | 最後の節が全体の12%を超える |

**いちばん大事な決まり: 目視で見つけたら、その場で直して終わりにせず、点検に足す。**
直すだけだと同じ種類が次の動画でまた出る。点検に足せば、次からは機械が拾う。
足すときは「壊れた例を食わせて × になる」テストも書く。**✓ しか出ない点検は、
壊れていても気づけない。**

`contact` の一覧は、その「目視で見つける」ための道具。面倒だと見なくなるので、
1コマンドにしてある。実際、初めて使った日に「7枚つづけて同じカードと同じ見出しで
40秒ぶん画面が変わっていない」ことが分かり、`見た目の変化` の点検になった。
